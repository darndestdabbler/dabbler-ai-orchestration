## 1. **Verdict, first.**

**Do part of it now and the rest later.**

1. **Ship folder-free configuration separately.** It fixes a known failure and needs no claim about documents.
2. **Walk a document through closure before freezing the new onboarding text.** Test the evidence and review contract, not merely whether execution stops.
3. **Repair routing before widening the invitation.** Existing code currently selects maintenance onboarding, which the plan largely exempts from the new questions. That can exclude someone writing that code’s operating procedure.

The configuration layers and keeping refinement inside a session are sound.

## 2. **The widening itself.**

The strongest objection is that this release extends a claim of reliable completion into work for which its evidence is weakest. Section checks establish structure. A second model supplies criticism. Neither establishes that legislation has the intended legal effect, a policy reflects current authority, or a novel achieves its author’s purpose. Automatic closure can make that distinction disappear.

The proposed walk compounds this: a two-page procedure with **no starting material** avoids source fidelity, citations, conflicting authorities, existing drafts and external edits. Those are central to the proposed audiences. Nor does walking PowerShell justify “programs in any language.”

That case wins against broad support claims, but not against removing needless code assumptions.

The smallest defensible release permits **text-only document drafting as a limited trial**, removes compulsory software questions, and reports exactly what was walked. Do not advertise policies, legislation and novels as established uses. The opening question can still accept them without listing them as promises.

Also, failure requiring a new design must block the relevant claim. “No waiver was needed” is too weak: an ordinary exit can still demand expert intervention a newcomer could not discover.

## 3. **Is the evidence honest for prose?**

It is verification of narrow facts, plus model review. It becomes the look of verification when described as proving a draft “whole,” or when “whether it is any good” is assigned to the reviewer.

The supplied reviewer contract mentions the session plan and non-goals, not assured access to the brief and source material. **Check this explicitly.** Merely asking the author to judge against those materials does not put them before the reviewer. A diff alone may also conceal contradictions with unchanged chapters.

Require each prose session to identify:

- The agreed requirements and relevant sources, with stable versions.
- The surrounding text needed to understand the change.
- What counts as an error: a missing requirement, unsupported factual claim, contradiction, broken reference or breach of an agreed rule.
- What remains a suggestion: alternative phrasing, structure or taste not required by the brief.

Every blocking finding should cite a requirement or source and state a concrete correction condition. New preferences must not become new obligations during review. Unresolvable questions go to the person. A round cap is an exit, not evidence of success.

Record structural checks separately from model findings. State what sources the reviewer received, what it did not receive, that suites were inapplicable, outstanding findings and the reason review ended. Add plainly:

> No person has approved this draft for use.

Remove that statement only when an actual approval is recorded.

## 4. **What round 25 got wrong.**

I would reverse or narrow four adopted items:

- **Item 6, “the reviewer judges the rest.”** Replace this with the bounded review contract above. That division gives the reviewer responsibility it cannot reliably discharge.
- **Item 7, text is authoritative.** Make this an explicit agreement, not a planning instruction imposed on every document. A legislative or policy office may already have an authoritative Word file with comments, numbering and tracked decisions. Exporting plain text can lose meaning. If that office cannot accept text as the working master, do not imply the workflow fits.
- **Item 8, notice without a pause.** The framework need not decide handling rules to ask someone to stop and choose. Session 1 is also too late for a brief already supplied in the authoring prompt. Put the notice before inviting material, offer a clear way to change providers, and ask for acknowledgment before further reading. Check actual reviewer inputs before claiming that all material goes to both.
- **Item 12, treating every listed extension as code.** `.rmd` and `.qmd` can contain prose without executable content. An extension alone should not impose code obligations. Test those cases before adding them wholesale.

Under **“What was not taken,” take the closure experiment before 331**. Reading two gates cannot establish end-to-end behaviour, useful review or honest closure.

Also take an **open first question**, with optional examples rather than four numbered categories. One opening sentence can invite unfamiliar uses without suggesting each has been validated. I would not require a separate session just for the release stamp.

## 5. **Session 1’s text, read two ways.**

For a newcomer, this current sentence loses them:

> Before any module is proposed, ask them how production is split: what runs separately in production, and which part may talk to the database?

Replace it with:

> Will any parts of the software run separately? If you are not sure, we can decide together. We only need to discuss a database if the work uses one.

The proposed conversation is friendlier, but the authoring model faces conflicting routing instructions. “One or more” categories permits mixed work, while the later branches look exclusive. The .NET branch preserves today’s architecture questions unchanged, even for an application needing no database. Maintenance onboarding may bypass the new goal question entirely.

Build the text from a common intake and clearly bounded conditional sections. Ask what is being changed **in every posture**. Apply conditions per deliverable, so a research paper and its analysis script get different checks. Treat detected build files as evidence, not the person’s intent.

Keep one generated scaffold if desired, but generate shared instructions from one source. Test empty, existing-code, existing-document and mixed-work cases. Tests that merely find the questions in the output do not test branch selection.

## 6. **The button.**

**Set Up New Project.** “Project” fits both writing and software, and keeping it avoids a rename without a clear benefit.

Keep all three actions, but only the relevant ones visible: two with no folder, one in an unconfigured folder. The current contextual arrangement is right. Check that the existing setup command really distinguishes creating a new folder from setting up the current one before changing its labels.

## 7. **What is hard to undo.**

Ranked:

1. **Scaffolded session instructions.** They remain in repositories after an upgrade. Stamp their template version and offer a reviewed update for sessions not yet started. Never silently replace local plans.
2. **Authority and information leaving the machine.** A sent document cannot be recalled; competing Word and text masters can corrupt decisions. Explain destinations before intake and record the agreed master before conversion or drafting.
3. **Historical completion claims.** Later fixes cannot make old reviews stronger. Record the evidence contract and its version, with separate structural, model-review and human-approval states.
4. **Routing by file type.** Once it selects onboarding and obligations, fixing detection does not repair existing plans. Keep detection provisional and provide an explicit correction path.
5. **Public support claims.** People build workflows around them. Publish the tested boundary and limitations rather than a list of aspirational audiences.

Labels are cheap to change. Stored instructions, records and user reliance are not.

## 8. **Order and release.**

**Yes, ship 330 alone first**, with “Project” retained and its versioning moved out of 333. Limit that release to configuration and the necessary setup navigation.

**Yes, walk a document before rewriting the final session 1 text.** Use a manually prepared scratch plan to test the existing lifecycle. Include source material, a seeded substantive error and a review that must consult unchanged text.

Then:

1. Fix the evidence, routing and reviewer-context problems the experiment exposes.
2. Implement 331’s revised intake and conditional instructions.
3. Walk the complete generated onboarding through closure, including pausing and resuming refinement.
4. Implement and walk 333’s script detection changes. Show how a required suite is established, not waived.
5. Run existing .NET and Java regression cases.
6. Write claims from the results, then release.

Keep session numbers. Split or amend their scope and execution order explicitly. The later walk must validate the generated experience; it cannot substitute for the earlier design experiment.

## 9. **The thing nobody has thought of.**

**A document session still commits and pushes.** Omitting a document “release session” does not prevent distribution.

Before the first document walk, inspect the remote, repository visibility and push behaviour. A novice may think “draft” means local and private. Say where closing a session sends it, before the session begins. Test the no-remote case too. Provider disclosure is only one destination; the repository is another.

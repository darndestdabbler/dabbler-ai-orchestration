**ISSUES FOUND**

**Issue 1:** The tracked, packaged router config was left in a seat-local `copilot-cli` transport profile.
- **Category:** Correctness
- **Severity:** Major
- **Failure scenario:** A normal Full-tier user or fresh clone/wheel install with provider API keys but no local Copilot catalog runs `route()`/`start_session`; the bundled config selects `copilot-cli`, skips API-key validation, then fails loading the ignored `ai_router/copilot-catalog.lock`. That is probable because the docs still present `api` as the normal/default profile and the catalog is intentionally not tracked.
- **Details:** **Violation:** docs say `transport.profile: api` is the default direct-HTTPS path and `copilot-cli` is an opt-in seat profile; the temporary Set 110-112 policy is documented as only `routing.outsourcing_mode: verification-only` plus the one-entry delegation list. **Impact:** the committed/package-data router config makes the router unusable on API-key-only machines, changing the merge decision for shared `ai_router` state. **Evidence:** `ai_router/router-config.yaml` sets `transport.profile: copilot-cli`; `pyproject.toml` packages `router-config.yaml`; `.gitignore` ignores `ai_router/copilot-catalog.lock`, and `git ls-files` confirms it is not tracked; `ai_router.__init__` raises if that lockfile cannot load under `copilot-cli`, while `config.py` skips provider API-key checks in that profile. Correct answer: keep the tracked config on `api`, or add a supported local override path for `transport.profile` and keep the Copilot seat choice out of shared/package data.

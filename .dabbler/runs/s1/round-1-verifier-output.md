- **Issue 1:** The recorded session-1 close strategy is unbuildable: it says to leave non-bookkeeping files uncommitted for session 2, but the close gate refuses any such dirty files.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `docs/session-sets/148-the-session-framework/decisions-log.md:47-67`, `ai_router/gates.py:158-200`, `ai_router/ledger.py:48-52`, `docs/session-framework-build-instructions.md:182-191`
  - **Failure scenario:** The operator follows D3, commits only `docs/session-framework-spec.md` and `docs/session-framework-plan.md`, leaves `docs/session-framework-build-instructions.md` and `docs/session-sets/148-the-session-framework/spec.md` for session 2, then runs `ai_router.session close`; the `working_tree_clean` gate rejects those files, so session 1 cannot close. This is probable because D3 explicitly instructs that state.
  - **Acceptance criterion:** `JUDGMENT - Session 1's close path no longer requires leaving any non-bookkeeping worktree file uncommitted; either those files are committed/removed before close, or the session split is changed so the close gate has no material dirty paths to reject.`
  - **Details:** **Violation:** session 1 requires “Close-out,” and the operating manual says close runs the “working_tree_clean” gate. **Impact:** the session cannot produce the verified/closed design record it exists to dogfood. **Evidence:** D3 says the build instructions and set spec “stay uncommitted as session 2's work product,” while `check_working_tree_clean` ignores only lifecycle bookkeeping and machine state; `spec.md` is explicitly absent from lifecycle-written files. The correct answer is to resolve the session boundary so close can pass without dirty non-bookkeeping files.

- **Issue 2:** The design keeps direct API verification as a supported path but misses that OpenAI direct API calls cannot authenticate.
  - **Category:** Completeness
  - **Severity:** Major
  - **Evidence paths:** `docs/session-framework-spec.md:39-69`, `ai_router/router-config.yaml:337-340`, `ai_router/transports/api.py:203-228`
  - **Failure scenario:** A no-seat/API-transport user runs session verification with an Anthropic or Google author; the configured `session-verification` override selects an OpenAI model, but `_call_openai` sends `Authorization: ******`, so every real OpenAI request fails authentication. This is probable for the supported “anyone without a seat” path because OpenAI is an enabled configured verifier.
  - **Acceptance criterion:** `JUDGMENT - The plan/spec either stop claiming OpenAI/direct-API verification is supported, or include/perform a concrete repair so OpenAI requests send the resolved API key in a provider-valid Authorization header without logging the secret.`
  - **Details:** **Violation:** the spec says direct API “stays supported” and verification remains cross-vendor “on either transport.” **Impact:** the supported fallback transport fails on a main configured verifier path, changing the merge decision for a framework that claims API transport remains usable. **Evidence:** `_call_openai` resolves `api_key` but never uses it in the request header. The correct behavior is an OpenAI-valid bearer authorization header built from the resolved secret.

ISSUES FOUND

- **Issue 1:** `verify step close` records a step as closed without committing it or advancing the baseline, so the documented multi-step flow breaks after the first step.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verify.py:1790-1805`, `ai_router/verify.py:1865-1901`, `ai_router/approved_plan.py:504-529`, `ai_router/gates.py:158-200`, `docs/quick-start.md:141-146`
  - **Failure scenario:** A normal approved plan has two steps with disjoint envelopes, e.g. `a.txt` then `b.txt`. The user follows the docs, opens/edits/closes step A, then opens/edits/closes step B without a manual commit because the docs say the framework commits the step. Step B is diffed against the same original `HEAD`, so step A’s still-uncommitted `a.txt` appears outside step B’s envelope and close refuses; if they continue to session close, the working-tree-clean gate also blocks. Multi-step approved plans are the intended path, so this is probable rather than exotic.
  - **Acceptance criterion:** `JUDGMENT - In a fresh repo with an approved two-step plan using disjoint envelopes, can the operator open/edit/close step A and then open/edit/close step B with no manual commit between them, with step B closing successfully and the closed step files not causing the final working-tree-clean gate to fail?`
  - **Details:** **Violation:** the task requires step-by-step execution, and the docs promise “**The framework commits the step; you do not.**” **Impact:** a reasonable reviewer would block because the core workflow cannot progress through multiple steps as documented. **Evidence:** `run_step_open` anchors each step to current `HEAD`, `run_step_close` compares against that base and appends only a closed ledger row, and no commit/baseline advancement occurs before returning success; the envelope comparison therefore includes previous closed-but-uncommitted work, and the close gate later refuses uncommitted files.

- **Issue 2:** Deterministic declaration errors do not block `step close`, so malformed suite/selection config can close a step without running the intended targeted tests.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verify.py:1715-1751`, `ai_router/verify.py:1874-1886`, `ai_router/affected.py:149-223`, `ai_router/test_evidence.py:197-235`, `ai_router/schemas/router-config.schema.json:170-172`
  - **Failure scenario:** A repo maintainer updates `testing.selection.rules` and misspells a key such as `select`, or misdeclares `testing.suites`. `load_config` accepts it because the schema leaves `testing` unconstrained; `step close` prints declaration errors but still proceeds if no required control is red, appending a closed event even though the intended targeted test mapping/suite was invalid. Maintaining repo-specific test mappings is routine for this workflow, so this is a probable configuration failure, not adversarial misuse.
  - **Acceptance criterion:** `JUDGMENT - With malformed testing.suites or testing.selection declarations, does verify step close return a nonzero refusal, leave the step open, and avoid appending a closed step-execution row until the declaration error is fixed?`
  - **Details:** **Violation:** the session requires “the step’s own targeted tests” to run in the deterministic pass before model spend. **Impact:** a step can be marked closed with false deterministic evidence, undermining the main gate this session is adding. **Evidence:** `_step_deterministic_facts` returns selection errors but discards suite-loader errors, and `run_step_close` only prints returned errors before continuing to `red_facts_refusal`; since that refusal only looks at red facts, declaration errors do not stop the closed ledger append.

ISSUES FOUND

- **Issue 1:** Same-step `workflow enter` clears the cap state and reopens fresh review rounds on the same step.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/workflow.py:145-160, ai_router/workflow.py:242-253, ai_router/workflow.py:676-680`
  - **Failure scenario:** A target reaches the cap on `plan` or `decompose`, the author edits the artifact, then runs `workflow enter <current-step>` before `workflow review` again. That path is accepted, and it zeroes `reviewRounds` and `lastLiveReview`, so the same step can spend another full set of vendor rounds. This is probable because there is no other CLI path to reopen review of that same step after edits without moving backward or forward, so `enter` is the obvious command a user will try.
  - **Acceptance criterion:** `JUDGMENT - After a target reaches any terminal review state, entering the current step again is refused (or at least leaves reviewRounds and lastLiveReview unchanged) so the same step cannot reopen more review rounds without a send-back or a real step change.`
  - **Details:** **Violation:** the task requires that “A step gets at most `verification.settings.max_rounds` review rounds” and that the loop land in one of the three terminal states rather than reopen. **Impact:** the new bound can be bypassed on the same step, so the claimed fix does not actually close the vendor-spend hole for users iterating within that step. **Evidence:** `validate_transition()` rejects only backward enters and skipped steps, so `to_index == current_index` is accepted (`ai_router/workflow.py:145-160`); `fold()` resets `reviewRounds` and `lastLiveReview` on every `entered` event (`ai_router/workflow.py:242-253`); and the `enter` command writes that event with no terminal or same-step guard (`ai_router/workflow.py:676-680`). The correct behavior is that only a send-back or a forward step change opens a new loop.

- **Issue 2:** `workflow review` and `workflow status` resolve the round cap from the caller's current directory, not the supplied workspace root.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/workflow.py:320-328, ai_router/workflow.py:399-405, ai_router/workflow.py:527-530, ai_router/workflow.py:643-648, ai_router/config.py:76-99, ai_router/config.py:107-124`
  - **Failure scenario:** A repository sets `local-overrides.yaml` to `verification.settings.max_rounds: 1`, and an operator or extension invokes `workflow status` or `workflow review --workspace-root <repo>` from some other working directory. `review_cap()` ignores `<repo>` and loads config via `Path.cwd()`, so enforcement and status/projection can use a different cap (typically the bundled default 3 or another repo's override), allowing extra vendor rounds and reporting the wrong bound. This is probable because the product explicitly supports `--workspace-root` and `project(root)` as first-class entrypoints.
  - **Acceptance criterion:** `JUDGMENT - With the process cwd outside the target repository, workflow status, workflow review, and the projection still resolve verification.settings.max_rounds from the supplied workspace root's config/local-overrides and use that same value for both display and enforcement.`
  - **Details:** **Violation:** the task says the loop is bounded by `verification.settings.max_rounds` and that `workflow status` plus the projection surface that round count/cap. **Impact:** on a supported invocation path, the code can overrun the configured cap and misreport it, which undermines the spend-control and visibility this session was supposed to add. **Evidence:** `_main()` accepts `--workspace-root` and passes that root into `project(root)` and `_run_review(...)` (`ai_router/workflow.py:643-648`), but both paths call `review_cap()` with no root (`ai_router/workflow.py:320-328`, `ai_router/workflow.py:527-530`). `review_cap()` then calls `load_config()` with no path (`ai_router/workflow.py:399-405`), and `load_config()` discovers project-local overrides from `project_root()`, which is derived from `Path.cwd()` rather than the supplied workspace root (`ai_router/config.py:76-99`, `ai_router/config.py:107-124`). The correct behavior is to resolve the cap against the target workspace, not the process cwd.

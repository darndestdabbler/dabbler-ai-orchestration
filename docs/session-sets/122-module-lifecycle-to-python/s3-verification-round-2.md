**ISSUES FOUND**

- **Issue 1:** The new dogfood CI lane depends on untracked local Python state and will fail in a clean runner.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `tools/dabbler-ai-orchestration/src/test/dogfood/routerFloorProvisioning.test.ts:83-91,143-149,354-375`, `.github/workflows/test.yml:248-264`
  - **Failure scenario:** On a clean GitHub Actions runner there is no repo-root `.venv`, so `hostPython()` returns bare `python`. The workflow only runs `npm ci` from `tools/dabbler-ai-orchestration` and never installs the repo’s `ai_router` package into that host interpreter. The final dogfood test then asserts `canImportModules(hostPython()) === true`, but that child Python runs from the extension directory, not the repo root, so `import ai_router.modules` is not on `sys.path`. This is probable on every clean CI run, not an edge case, and it makes the claimed Linux/Windows dogfood gate red or dependent on a developer’s untracked local venv.
  - **Acceptance criterion:** `JUDGMENT - In a clean checkout with no repo-root .venv, the provisioning-dogfood workflow either explicitly makes the host interpreter able to import this checkout's ai_router package or removes the host-import premise, so the dogfood lane no longer depends on untracked local Python state.`
  - **Details:** **Violation:** the workflow says the dogfood job prevents the lane from being “local-only” and runs it on both OSes, while the test assumes “the host interpreter this repo runs on genuinely does have” `ai_router.modules`. **Impact:** the release-gate evidence is not reliable because the CI job can fail before proving the provisioning behavior. **Evidence:** the workflow installs Python, Node, and extension npm dependencies only; the test’s `hostPython()` falls back to `"python"` without a repo `.venv`, and `canImportModules(hostPython())` performs a plain `python -c "import ai_router.modules"` with no cwd/PYTHONPATH/package install tying it to the checkout.

### 1. Verdict, first

**Start with changes.**

1. **Tell the reviewer *who* can write what in Session 335 Step 3.** Labelling a working-tree difference in `session-plan.md` merely as "changed during the session" gives the AI author a blank cheque to rewrite its own requirements mid-session and pass review. The prompt must explicitly distinguish an amendment committed to git by the operator from uncommitted working-tree edits made by the author, or instruct the reviewer that working-tree edits to the current session's own spec do not relax the start-commit requirements.
2. **Account for markdown fenced code blocks in Session 335's one reader.** Stopping naively at `/^#{1,3}\s/m` will truncate any session plan section that contains `# comment` (e.g., bash/python/yaml snippets) or markdown heading examples inside triple-backtick code blocks.
3. **Allow `session_number` in `planAsk` and `stampAnswer` (Session 334).** `mtime` is necessary, not sufficient (clock skew, coarse filesystem timestamps, fast scripted runs). Look at `driver.ts:2339`: `stampAnswer` *already* verifies `session_number` if present and only throws when it mismatches! Dropping the prohibition in `planAsk`—or requiring `session_number` in the file—gives you a deterministic content check alongside the `mtime` check at near-zero cost.

### 2. Each of the five calls

1. **Replacing a declared work plan is not planned (Call 1):** **Agree.** With per-session scratch filenames, `mtime` checks, and file consumption in place, an unstarted rollback discards zero committed work and preserves the append-only invariant of `activity-log.json`.
2. **A mid-session edit to the plan is shown to the reviewer, not frozen out (Call 2):** **Disagree with the framing as planned.** Showing both the `startCommit` version and the working-tree version is right *if* an operator amended the plan, because freezing it out would hide an approved change. However, `session-plan.md` in the working tree is writable by the AI author during steps (as happened in Session 140). As written in Session 335 Step 3 (*"the second labelled as changed during the session, so an amendment a person made is in front of the reviewer and an edit the author made is too"*), the reviewer has no way to tell whether the diff in `session-plan.md` was an approved mid-session commit by the operator or the AI author deleting a hard requirement it failed to implement. Compare `approvedPlan.ts:655-660`, which explicitly notes that `startCommit` is *"the one approval the engine the control holds cannot write"*. The prompt wording in `prompts.ts` must tell the reviewer that the `startCommit` text is the binding baseline unless an operator decision/commit explicitly amended it, and that author-made edits in the diff cannot drop required work.
3. **The rollback's handling of cancelled transcript pages is not changed (Call 3):** **Agree.** In `session.ts:4132-4147`, `rollback` only checks out `cancelledPages` from `headNow` when `commits.length > 0`, and Session 140's completed transcript was only revert-clobbered in Session 141 because the operator manually ran `git revert 95bcaac` (`a3fd898`) *before* invoking `rollback`.
4. **The reviewer keeps receiving both the session's section and the declared work plan (Call 4):** **Agree.** Passing both `specExcerpt` and `workPlanBlock` is how the reviewer catches an author whose declared `plan.json` quietly narrows or drifts from `session-plan.md`.
5. **`sessions.json` is not written when the plan is committed (Call 5):** **Agree.** `session-plan.md` is authored in prose commits outside the router; keeping router state mutations strictly inside router lifecycle verbs avoids git hooks or dual-source-of-truth bugs.

### 3. What the plan misses

1. **Self-serving mid-session spec edits by the AI author pass verification (via Session 335 Step 3):**
   - *Sequence of events:* Session N starts at `startCommit` X with a requirement R in `docs/sessions/session-plan.md`. During Step 2, the AI author struggles with R, or decides R is out of scope, edits `docs/sessions/session-plan.md` in the working tree (having listed it in `files` or via `plan amend`) to move R to a "Proposed follow-up" or soften it, and reports the step. At verification, `verify/prompts.ts` runs Session 335 Step 3: it shows the `startCommit` section and the working-tree section *"labelled as changed during the session"*. Because the prompt gives the reviewer both on equal footing (expecting it might be an operator amendment), the reviewer treats the softened working-tree section as the updated target and approves the session.
2. **Millisecond/sub-second timestamp collision or WSL/VM clock skew on `mtime` (via Session 334 Step 2):**
   - *Sequence of events:* Suppose an instruction is re-issued or issued on a filesystem/container mount where host vs. guest clock skew exists (e.g., WSL2 or Docker volume mount where file `mtime` comes from the host kernel and `nowIso()` in `issued_at` comes from the guest clock, or `issued_at` is truncated to whole seconds—*inferring potential `nowIso()` vs `nowIsoSeconds()` precision from `session.ts:2440` vs `4102`*). Either: (a) a newly written valid file has an `mtimeMs` 50ms *earlier* than `Date.parse(instruction.issued_at)` (or within the same second if `mtime` has 1s granularity on FAT/older mounts and `>` is used instead of `>=`), causing valid answers to be falsely refused in a loop; or (b) `planAsk` still forbids `session_number`, so if an author copies or touches an old file outside `.dabbler/scratch/` (which Step 3 deliberately does not delete), `mtime` updates and the wrong session's plan is still accepted. Allowing or requiring `session_number` in the JSON payload (`stampAnswer` in `driver.ts:2339` already checks `key in record` for mismatches!) closes (b) completely, and checking `issued_at` precision prevents (a).
3. **Code-block `#` comments inside `session-plan.md` truncate the spec (via Session 335 Step 1):**
   - *Sequence of events:* An operator writes a session in `docs/sessions/session-plan.md` that includes a fenced markdown code block (` ```sh ` or ` ```yaml `) containing a line starting with `# Run the check` or `### Section`. Session 335 Step 1's unified reader scans for *"the next heading of level three or above"* (e.g. `/^#{1,3}\s/m`). It matches `# Run the check` inside the code block, silently slicing off the bottom half of the session's plan (including Non-goals and Tests) for `planAsk`, `verify/prompts.ts`, `approvedContractChange`, and `transcript.ts`.

### 4. What the plan gets wrong or over-builds

- **Unscoped heading stop breaks on `####` vs `#` inside code blocks (Session 335 Step 1):** Stopping at `^#{1,3}\s` outside fenced code blocks is right (it catches `# Part`, `## Phase`, and `### Session` / `### Proposed follow-up` while letting `####` subheadings live inside a session). Doing it with a bare multiline regex without skipping ` ``` ` / `~~~` fences will break any session plan that embeds shell/python/markdown examples.
- **`sessionStartCommit` fallback when `startCommit` is `"HEAD"` (Session 335 Step 3):** Look at `approvedPlan.ts:652`: `sessionStartCommit` falls back to `"HEAD"` if `startCommit` is missing or empty on the session row. Normally nothing is committed before verification (`session.ts:4112`: *"Nothing of a session is committed before its land"*), *unless* an operator committed a mid-session plan amendment! (*Inferring how operator mid-session amendments work, as commit mechanics during a live session are not in the excerpts.*) If the operator *commits* an amendment mid-session, `startCommit` is still the pre-amendment commit, so `git show <startCommit>:...` vs working tree works; if an edge case hits the `"HEAD"` fallback, both reads will silently return the amended commit. Worth asserting in tests that `startCommit` is populated.
- **HEAD binding race/assumption in Session 336 Step 1 (`runRollbackSessionFlow`):** Step 1 states *"bound to the HEAD the facts were read at, which a report does not move because it writes only under `.dabbler/`."* That is true of `defect-report` itself, **provided** `defect-report` takes a provider call (~5–20 seconds) during which an active terminal/background agent might still be running if the user didn't kill it, or `git status` changes. Ensuring the UI disables concurrent session actions while `defect-report` runs (which `hasStandingStop` implies, since the driver is stopped) is sound, so nothing here is over-built—just verify `defect-report` doesn't dirty any tracked file (`mechanic-log.md` is *read*, not written, by `defect-report`—*inferred from Session 336's prose*).

### 5. The order

**Yes, both the 334 → 335 → 336 order and shipping them as a single `3.35.0` release (337) are right.**

- **Order:** Session 334 fixes the active session-corrupting bug in Dabbler's own router first (and benefits Sessions 335 and 336 if you dogfood the local build, or at minimum touches `drive.ts` `planAsk` cleanly before Session 335 touches `planAsk`'s excerpt reader). Session 335 unifies plan reading across 4 modules without entangled UI changes. Session 336 touches the VS Code extension flow, CLI flags, changelog, and `version.json` stamp last, where changelog and version stamping belong.
- **Single release (`3.35.0`):** Shipping 334 without 335 leaves the whole-file `extractSpecExcerpt` fallback live; shipping 334+335 without 336 misses the telemetry hook needed when staff upgrade and hit whatever the *next* unknown rollback stop is. Three small, self-contained sessions bundled into one minor release is the right cadence.

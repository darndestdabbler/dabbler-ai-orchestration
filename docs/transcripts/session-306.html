Session 306 of 309: The build contract holds

Scope: packages/router/src/facts.ts (the contract control), packages/router/src/solutionDeps.ts (the XML reads it reuses), packages/router/src/checks.ts (the control at a step's checks), packages/router/src/verify/ (what the verifier is told), packages/router/src/approvedPlan.ts and packages/router/schemas/approved-plan.schema.json (the plan's contract_change), the tests named after each, docs/driving-a-session.md

Why. The rule in the managed body says keep the target; a rule in prose is advice, and an engine under pressure to make a test pass upgrades a TargetFrameworkVersion, adds <Nullable>enable</Nullable>, bumps a package in packages.config or writes <maven.compiler.release> into a POM that built on JDK 8. Each of those compiles here and breaks in Visual Studio, IntelliJ or Eclipse on the next developer's machine, which is the one failure the maintenance posture exists to prevent. The advisors split on how to hold it: one would compare evaluated MSBuild properties and the effective POM, the other would diff the declared elements against HEAD. The diff is taken: it needs no toolchain, no stored baseline and no new state, and every edit an engine can make to those files is visible in it.

What. A deterministic control, contract, that compares the elements which decide what a project builds as between the working tree and HEAD, and refuses a step whose diff moves one.

Step 1 -- the contract, read. facts.ts gains a reader that, for every build file in the project graph, extracts the elements that fix the target: for a .csproj or .fsproj, the root element's Sdk and ToolsVersion attributes and the TargetFramework, TargetFrameworks, TargetFrameworkVersion, TargetFrameworkProfile, LangVersion, Nullable and ImplicitUsings properties, plus Directory.Build.props and global.json where they exist; for packages.config, every package entry's id, version and targetFramework; for Web.config and App.config, the compilation and httpRuntime targetFramework attributes; for a pom.xml, packaging, parent, the java.version and maven.compiler.source, target and release properties, the compiler plugin's source, target and release, and the toolchains plugin's jdk; for .mvn/wrapper/maven-wrapper.properties, the distributionUrl; for Gradle, sourceCompatibility, targetCompatibility, the toolchain's languageVersion and the wrapper's distributionUrl. The XML reads reuse solutionDeps.ts. The same reader runs over git show HEAD:<path>, and the two readings are compared element by element.

Step 2 -- what the comparison says. A changed element is a failure naming the file, the element, the value at HEAD and the value in the tree. A build file deleted from the tree is a failure. A build file new in the tree -- a test project the session adds -- has nothing to compare and passes, with its target recorded in the detail. Under maintenance, every .cs or .vb file added under a non-SDK project's directory must appear as a Compile item of that project, and every .cshtml, .aspx or .ascx as a Content item; a file that does not is a failure naming it, because Visual Studio would not see it. The control is not_applicable under greenfield, and dabbler facts records it like any other.

Step 3 -- at the step, not only at the end. checks.ts runs the contract control among a step's own checks under maintenance, so a report whose diff moves the target is refused at the report with the element named, and the engine fixes it in the same step rather than learning at the round. The verifier is told the posture, the contract and the control's result, so a reviewer reading a diff that touches a build file knows what it was held to.

Step 4 -- the human way out. A target change is sometimes the work: the shop moves a service from 4.5.1 to 4.8. The plan carries contract_change, naming the files whose contract may move and the reason; the person approves it with the plan; the control then reports not_applicable for those files and pass or fail for the rest, and the record carries the approval. There is no flag on a report, no override in a step and no environment variable: the plan the person approved is the whole of the way.

Non-goals. Evaluated MSBuild properties or an effective POM. A stored baseline of any kind. A control that reads package versions for SDK-style PackageReference items: those are the engine's to change within the target, and the review reads them. Any hold on application code.

Tests. In facts.test.ts, each on a fixture tree with a HEAD: a non-SDK .csproj whose TargetFrameworkVersion moved is refused naming both values; an SDK .csproj that gained Nullable is refused; a packages.config entry bumped is refused; a POM that gained maven.compiler.release is refused; a wrapper whose distributionUrl moved is refused; a new test .csproj passes with its target recorded; a new .cs under a non-SDK project with no Compile item is refused naming the file, and with one passes; greenfield is not_applicable. In checks.test.ts: under maintenance a step's checks include the control and its failure refuses the report. In approvedPlan.test.ts: a plan naming contract_change for one file makes that file not_applicable and leaves the others held.

Releasable. No -- as 3.31.0 in session 309.

ISSUES FOUND

- **Issue 1:** The version-1 migration still strands valid repository journals containing multiple session sets or set-level lifecycle events.
  - **Category:** Completeness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/journal.py, tests/test_journal.py`
  - **Failure scenario:** A repository-level journal accumulated runs from two session sets under the previous set-based machinery, then the repository upgrades to the collapsed session model. This is probable for any long-lived repository that completed more than one set—the old events carried `set_slug` specifically to distinguish those histories. `read_events()` now raises `JournalCorrupt` before exposing any events, so commands cannot read either the historical sets or the current set that the session plan requires migrating. A valid single-set journal is likewise stranded if it contains a valid set-level cancellation/restoration event.
  - **Acceptance criterion:** JUDGMENT - A valid schema-version-1 repository journal containing multiple set slugs and valid set-level lifecycle history can be read or deterministically migrated without `JournalCorrupt`, while preserving distinct historical identities and making the active set’s sessions usable under repository-wide session machinery.
  - **Details:** **Violation:** The plan requires, “**Migrate this set's own state rather than abandoning it**,” while the implementation itself claims “the journal is durable history and a router upgrade must not strand it.” **Impact:** If this set shares the repository journal with an earlier set, the unconditional multi-set refusal prevents migration of this set too, blocking subsequent session registration and verification; that materially defeats the collapse migration and should block merge. **Evidence:** `upgrade_v1_records()` explicitly raises when `len(slugs) > 1` and separately raises for `payload["target"] == "set"`. `tests/test_journal.py` codifies both refusals rather than testing migration. The migration must preserve or archive legacy identities deterministically while still allowing the active state to proceed, rather than rejecting the entire durable journal.

**NITS**

- **Nit:** The re-anchor fix materially resolves the prior first-post-round-anchor defect for normally ordered timestamps. However, `_legal_anchor()` still equates Git’s second-resolution, user-controlled committer timestamp with actual commit chronology; a remediation commit with an equal or backdated timestamp can still become the selected “at or before” anchor. This is a low-probability clock-skew or timestamp-manipulation case rather than a typical-user blocker.

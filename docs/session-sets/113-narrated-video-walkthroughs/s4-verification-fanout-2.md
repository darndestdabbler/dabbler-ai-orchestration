### Issue 1: A recorder is exposed despite the authoritative pilot verdict being `FAIL`
- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/package.json, tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js, docs/session-sets/113-narrated-video-walkthroughs/s4-pilot-criteria.json, docs/session-sets/113-narrated-video-walkthroughs/s4-os-capture-measurement.json`
- **Failure scenario:** A typical internal user follows the documented `npm run walkthrough:vscode` path and uses a recorder that the fixed criteria explicitly disqualified. This is probable because the command is registered and documented without any provisional gate, while the recorded verdict is `FAIL`; users cannot distinguish “present pending approval” from shipped functionality.
- **Acceptance criterion:** `JUDGMENT - While the authoritative verdict remains FAIL and no operator waiver exists, the Windows recorder must not be invocable or documented as available; alternatively, a new measurement must produce PASS before it is exposed.`
- **Details:** **Violation:** The plan says “only on a pass” does the session ship a recorder, and the criteria repeat, “Any criterion unmet ... is a FAIL. A fail ships no recorder.” **Impact:** The tree bypasses the release gate and the operator’s reserved decision by exposing functionality that failed C2 and C7, changing the merge decision from measurement-only to shipping an unapproved capability. **Evidence:** The measurement records `"verdict": "FAIL"`, but `package.json` registers `walkthrough:vscode` and the complete recorder is present. Calling it “provisional” in prose does not enforce a gate. **Fix:** Remove or disable the command and recorder until a passing measurement or explicit operator-authorized waiver exists.

### Issue 2: Several capture failures still destroy the walkthrough instead of degrading to no video
- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js, tools/dabbler-ai-orchestration/scripts/obs-capture.js`
- **Failure scenario:** An extension developer has another Extension Development Host open, causing `_chooseWindow()` to raise its documented ambiguity error, or OBS accepts `StartRecord` but never activates its output. Both are realistic on the intended developer workstation. The error escapes the narrow setup catch, `result.usable` remains false, the output directory is deleted, and the command exits unsuccessfully—so the user loses the written walkthrough and manifest as well as the video.
- **Acceptance criterion:** `JUDGMENT - Induced window-ambiguity and recording-start/stop failures must each clean up OBS and still complete the driven walkthrough, finalize the manifest/index, emit zero os-video artifacts, and return the documented degraded result.`
- **Details:** **Violation:** The implementation claims “FAILURE TO RECORD MUST NEVER FAIL THE WALKTHROUGH.” **Impact:** Common capture-specific failures erase the primary no-video deliverable, materially defeating the manual-only degradation contract. **Evidence:** Only `prepareHost()`, `launch()`, and `configure()` are inside the `ObsUnavailableError` degradation catch; non-`ObsUnavailableError` configuration failures are explicitly rethrown, and `startRecording()`/`stopRecording()` run outside that catch. The outer catch marks the whole run failed, and the `finally` block removes `outDir` when `result.usable` is false. **Fix:** Treat capture backend failures—including ambiguity and output start/stop failures—as video-unavailable outcomes after cleanup, while allowing genuine driver/scenario failures to remain fatal.

### Issue 3: The shipped path silently enables obs-websocket despite documentation and an unresolved operator decision saying it does not
- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/obs-capture.js, tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js, docs/walkthroughs/README.md, docs/session-sets/113-narrated-video-walkthroughs/s4-uat-walk.md`
- **Failure scenario:** A first-time user has OBS installed with its websocket disabled—the explicitly supported missing-dependency state—and runs the command expecting a no-video walkthrough. The recorder instead rewrites OBS’s configuration and enables the server without consent. This is the normal state targeted by guided-look decision B, and an interrupted process can leave that setting enabled.
- **Acceptance criterion:** `JUDGMENT - With server_enabled=false, the shipped command must leave the OBS configuration byte-for-byte unchanged and degrade to no video unless the operator explicitly authorizes automatic toggling and the implementation and documentation are changed consistently.`
- **Details:** **Violation:** The README says enabling the server is a manual prerequisite, the guided look says “what ships today” is that the tool never edits another application’s configuration, and disabled websocket is documented as a supported degradation path. **Impact:** The implementation silently takes an unresolved human decision and modifies external application state on the main path, undermining the privacy and trust boundary around OBS. **Evidence:** `prepareHost()` changes `cfg.server_enabled` to `true`, and `recordVscodeWalkthrough()` calls it unconditionally whenever video is requested. Restoration afterward does not make the initial unauthorized mutation equivalent to the documented manual-only behavior. **Fix:** Remove automatic configuration mutation from the shipped recorder unless the operator explicitly selects that policy.

### Issue 4: C6 is reported `PASS` without exercising or verifying the cleanup obligations fixed in the criteria
- **Category:** False Positive
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/os-capture-verdict.js, tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js, docs/session-sets/113-narrated-video-walkthroughs/s4-pilot-criteria.json, docs/session-sets/113-narrated-video-walkthroughs/s4-os-capture-measurement.json, docs/session-sets/113-narrated-video-walkthroughs/s4-os-capture-outcome.md`
- **Failure scenario:** The operator accepts the silent audio track and relies on the reported C6 pass when deciding whether to allow the recorder. A later configure/driver failure leaves VS Code running or temporary state behind, but the recorder suppresses the close/removal error and still reports no cleanup problem. This is probable enough for an automation path coordinating OBS, Electron, files, and forced process termination, and it materially affects whether the recorder is safe to authorize.
- **Acceptance criterion:** `JUDGMENT - A re-run must include an induced failure after OBS scene/profile creation and independently verify every C6 requirement, while the evaluator must fail C6 when that induced result or any required cleanup observation is absent.`
- **Details:** **Violation:** C6 requires cleanup “including when the run fails part way,” with an induced mid-run failure and explicit checks for the OBS process, scene collection, profile, VS Code process, run-directory leftovers, websocket configuration, and sentinels. **Impact:** The guided decision is presented with a false cleanup pass; accepting the two disclosed waivers can expose a recorder whose external-state cleanup was never established on the relevant failure path. **Evidence:** The committed measurement has `"inducedFailure": null`. The evaluator ignores that field and treats dependency-absence setup failures as sufficient. It only checks arrays named `cleanupProblems`; meanwhile `recordVscodeWalkthrough()` swallows `app.close()` and temporary-directory removal errors and never verifies that the VS Code process is gone or that run-directory temporary files are absent. The outcome also admits the configure-rethrow cleanup fix landed after all measured captures. **Fix:** Add the promised post-configuration induced failure, collect independent observations for every C6 requirement, fail closed when an observation is missing, and remeasure.

## NITS

- **Nit:** `--evaluate-only` rewrites `criteriaSha256` to the current criteria before reevaluating, and `--supplementary-run` does not reject a digest mismatch. This can rebind old captures to later criteria rather than detecting post-capture changes. Preserve the original digest and fail on mismatch. Location: `tools/dabbler-ai-orchestration/scripts/measure-os-capture.js`.
- **Nit:** Supplementary runs count toward `cleanRuns` using only usability, completed-step count, nonzero bytes, and contamination status; their C1–C4 observations, cleanup, and audio are excluded from criterion evaluation. A bad supplementary capture can therefore satisfy the ten-run count. Location: `tools/dabbler-ai-orchestration/scripts/os-capture-verdict.js`.
- **Nit:** C7 requires every captured window to belong to a harness-launched process, but selection only matches title/executable text and the evaluator never checks process ownership. Location: `tools/dabbler-ai-orchestration/scripts/obs-capture.js, tools/dabbler-ai-orchestration/scripts/os-capture-verdict.js`.
- **Nit:** obs-websocket requests have no response timeout. A connected but unresponsive OBS can hang setup, recording, or cleanup indefinitely instead of taking the documented degradation path. Location: `tools/dabbler-ai-orchestration/scripts/obs-websocket-client.js`.
- **Nit:** Cleanup removes every scene/profile entry that appeared after its snapshot and deletes all current sentinel files. Concurrent OBS activity or a second recorder can therefore lose operator-created state, while pre-existing sentinels are not restored. Location: `tools/dabbler-ai-orchestration/scripts/obs-capture.js`.
- **Nit:** Cleanup exceptions in the dependency-unavailable branch are swallowed after `capture` is cleared, preventing the `finally` block from retrying and leaving `cleanupProblems` falsely empty. The CLI also logs cleanup problems without failing. Location: `tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js`.
- **Nit:** `validateDriverBlock()` claims to reject driver-block typos but does not validate required `rowText` values or supported `click`/`then` shapes; malformed mechanics can silently select the first row or perform no action. Location: `tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js`.

**ISSUES FOUND**

- **Issue 1:** The API freshness check collapses all vendors to one record-level timestamp, so a partial enumeration failure still reads as fresh.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/discovery.py:489-510`, `ai_router/discovery.py:544-595`, `ai_router/discovery.py:709-757`, `ai_router/discovery.py:950-956`, `ai_router/session.py:564-565`, `ai_router/router-config.yaml:10-52`
  - **Failure scenario:** On the shipped three-provider config, one vendor key expires or one models endpoint is down while another vendor still answers. `enumerate` records the failure, but `merge_record()` advances `meta.enumerated_at` as soon as any provider succeeds, and `status` / `session start` only read that single timestamp. The API record is therefore reported fresh even though one provider's entries are stale. Partial provider failure is an expected operational path here, not an edge case.
  - **Acceptance criterion:** `JUDGMENT - Does the status/session-start freshness path keep a failing or not-currently-enumerated enabled vendor visible, instead of marking the whole API record fresh from another vendor's success?`
  - **Details:** **Violation:** "Enumerate each vendor's models endpoint..." plus "One staleness check reading both records: warns..." is not satisfied when only part of the record is current. **Impact:** the main maintenance signal can go green while one provider's discovery data is stale, which materially undermines a core deliverable of this session and would change a reasonable merge decision. **Evidence:** provider failures are intentionally first-class results (`ai_router/discovery.py:489-510`), but the only freshness date surfaced is the single record-level `meta.enumerated_at` updated on any success (`ai_router/discovery.py:544-595`, `ai_router/discovery.py:709-757`). **Correct answer:** freshness must either be conservative across enabled providers or explicitly report provider-level failure/staleness.

- **Issue 2:** The new API record is written inside `ai_router/` and explicitly published as package data, so the "local, regenerated, not shipped" invariant is not implemented.
  - **Category:** Completeness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/router-config.yaml:111-113`, `ai_router/discovery.py:628-632`, `ai_router/discovery.py:910-946`, `pyproject.toml:33-39`
  - **Failure scenario:** A maintainer runs `python -m ai_router.discovery enumerate` in the repo and then builds a package from that same tree. The command writes `ai_router/api-models.lock`, and `pyproject.toml` opts that filename into package data, so the build can ship a key-set-local discovery record to every consumer. That is a normal workflow for this feature, not a contrived misuse.
  - **Acceptance criterion:** `JUDGMENT - After running discovery enumeration in a working tree, is the resulting api-models.lock kept out of published artifacts (or written outside ai_router/) so a build cannot ship a local key-set record?`
  - **Details:** **Violation:** the session declared that the record "is seat/key-set local and is regenerated, not shipped." **Impact:** release artifacts can carry non-local discovery state and mislead fresh installs about what their own credentials expose, which breaks the session's releasability claim and changes the merge decision. **Evidence:** the default config resolves the record to `ai_router/api-models.lock` (`ai_router/router-config.yaml:111-113`, `ai_router/discovery.py:628-632`), `enumerate` writes that path (`ai_router/discovery.py:910-946`), and packaging explicitly includes it (`pyproject.toml:33-39`). **Correct answer:** keep the generated record out of package data and/or move the default write path out of the published package tree.

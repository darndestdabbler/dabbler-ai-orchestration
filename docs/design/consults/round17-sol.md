# Consult round 17 — gpt-5.6-sol via the Copilot seat (92 s; served gpt-5.6-sol)

1. **The shape.** **Recommendation:** Build only durable crash recording plus bounded automatic restart; defer the owner table and mechanic until real evidence identifies stops they would resolve. · **Design:** Treat “stale heartbeat, no recorded `Stop`” as an abnormal loop exit because intentional stops are already persisted in `driver/run.json` (`packages/router/src/drive.ts`, final catch and `renderStop`). Append the exception or process-exit evidence to `driver/supervision.jsonl`, preserve the loop log, and restart from durable state; the accepted plan is already idempotently reused. Do **not** write each uncaught exception as a terminal `Stop` and simultaneously declare that recorded stops are never restarted—that makes the two rules contradictory. Write the terminal `engine/loop-crash-repeated` stop only after retries are exhausted. · **The one risk:** Restarting can repeat a non-idempotent action performed immediately before the crash. · **Mitigation:** Restart only from persisted phase boundaries, and audit each deterministic operation for idempotency before enabling supervision around it. · **Delete:** Delete layers 2 and 3 for now; they do not address the observed failure, whereas crash recording and restart directly cover the incident.

2. **The supervisor.** **Recommendation:** The VS Code extension should supervise the loop, with two restarts per unchanged durable progress point. · **Design:** The extension already owns loop startup, checks the heartbeat, and implements idempotent Resume (`tools/dabbler-ai-orchestration/src/commands/sessionCommands.ts`, `runResumeSession`), so automatic Resume is the smallest change. The waiter must remain observational because the AI CLI and waiter can disappear; the loop cannot reliably relaunch itself after its own process has died. Key the bound by durable progress identity—phase plus outstanding instruction or equivalent persisted identifier—resetting it when durable progress occurs; after the initial crash plus two failed restarts, write an `engine` stop with a specific crash code and an explicit forced-retry command. Write an append-only log under `driver/` directly from the loop and also emit to the terminal best-effort; the incident proves terminal output alone is unavailable when the editor’s GUI-subsystem executable hosts Node. **ASSUMPTION:** The extension can run a lightweight heartbeat watcher while the VS Code window remains open. · **The one risk:** Two active loops could be launched during a heartbeat race. · **Mitigation:** Add a framework-owned atomic lease containing process identity and expiry; heartbeat inspection alone is not sufficient mutual exclusion. · **Delete:** Do not make the waiter restart anything, and do not create a detached self-relaunching loop; both introduce another lifecycle owner.

3. **The owner table.** **Recommendation:** Do not build the owner table yet; a taxonomy that does not perform recovery is documentation disguised as machinery. · **Design:** Keep the closed kind/code definitions in `packages/router/src/generated/driver-run.ts` and require every terminal stop to render at least one valid “way on” through `renderStop` (`packages/router/src/drive.ts`). Known deterministic cures should run before a stop is emitted; “framework-owned stop” is therefore a contradiction. If routing becomes necessary later, a reasonable initial mapping is: `budget`, `rejected-thrice`, and `interrupted` to human; `blocked`, `engine`, `tree`, `tests`, `verification`, `land`, `publish`, and `close` to AI troubleshooting after bounded framework retries. Codes such as `provider-unreachable` and `reviewer-unreachable` need bounded deterministic retry before that routing, while acceptance disputes such as `dispute-refused` or `cap-disputed` may require human authority; this shows why kind-only ownership is too coarse. · **The one risk:** A new stop can still ship without a useful exit. · **Mitigation:** Test the property that every kind/code combination has a rendered, executable forward path—not that every value has an abstract owner. · **Delete:** Delete the four-owner table and its completeness test; replace it with a forward-exit completeness test.

4. **The mechanic.** **Recommendation:** Defer the mechanic until supervised sessions produce a measured set of repeated stops that ordinary authoring AI cannot remediate. · **Design:** If evidence later justifies it, reuse the verifier agency protocol and audit trail from `packages/router/src/agency.ts`, but not its current authorization policy: that policy deliberately permits only one write under declared test roots. The minimum operations are list, search, read, write or patch within the workspace, and execute a command through a framework-controlled runner with fixed working directory, timeout, output capture, and cancellation. Count every operation equally; simple total-call accounting is easier to understand than separate “nearly free” reads and weighted mutations. Use a fresh conversation with the configured model, not a mandated third model; fresh context addresses assumption lock-in without adding provider policy. · **The one risk:** A mechanic with workspace writes and command execution can damage the tree or bypass lifecycle controls. · **Mitigation:** It must never edit `.dabbler/runs/` or the session ledger, write verdicts or gates, commit, push, publish, close, approve its own result, alter installed framework code, access paths outside the workspace, or suppress framework checks; success is established only by rerunning the failed framework operation and its checks. · **Delete:** Delete the mechanic lease from the current build; collect stop frequency, cause, and successful human/AI remedy first.

5. **The AI side.** **Recommendation:** Do not automatically resurrect an AI CLI or conversation; losing that process legitimately requires the operator to start a new engine conversation. · **Design:** The loop can detect an overdue instruction through its existing supervision events, but it cannot safely distinguish a dead AI from a slow or interrupted one (`driver/supervision.jsonl` records events such as `instruction-overdue`). Automatically launching another agent risks two authors modifying the same tree. If the loop is alive, Resume is not the answer—the extension should say to reopen the engine CLI and run `dabbler session wait`; if both are dead, the extension first restores the loop automatically and the operator then restores the interactive AI. Resume already refuses to start another live loop by checking the heartbeat (`tools/dabbler-ai-orchestration/src/commands/sessionCommands.ts`, `runResumeSession`). · **The one risk:** The operator may not know whether the loop or the AI died. · **Mitigation:** Show the two statuses separately: “loop recovered/running” and “AI client absent or overdue,” with exactly one corresponding action for each. · **Delete:** Do not add AI-process watchdogs, chat relaunch, or duplicate-agent failover.

6. **The one thing to prove first.** **Recommendation:** Fault-inject a hard loop termination at the exact incident boundary—accepted plan persisted, first instruction not yet declared—and measure whether recovery is correct without human action. · **Design:** The experiment passes only if the supervisor detects the stale heartbeat, preserves an actionable file log and supervision event, starts exactly one replacement, reuses the accepted plan, emits the first instruction exactly once, and converts repeated crashes at that same progress point into a recorded stop after two restarts. Also terminate through a normal recorded `Stop` in the same experiment to prove that intentional stops are not restarted. · **The one risk:** A happy-path restart can conceal duplicate work or a race between supervisors. · **Mitigation:** Judge persisted events and instruction identities, not merely whether the session eventually continues. · **Delete:** Do not build broader recovery policy until this experiment proves that one lifecycle owner can distinguish crash, intentional stop, and durable progress reliably.

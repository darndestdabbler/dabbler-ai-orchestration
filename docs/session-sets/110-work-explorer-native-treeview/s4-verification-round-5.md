ISSUES FOUND

- **Issue 1:** Round 4’s remediation is incomplete: the extension still writes the seat-local `copilot-cli` transport into shared `router-config.yaml`.
  - **Category:** Correctness
  - **Severity:** Major
  - **Failure scenario:** A typical Full-tier Copilot-seat user follows the primary guided setup or runs `Dabbler: Set Up Copilot Seat`; once the probe confirms two providers, the shipped extension writes `transport.profile: copilot-cli` into the workspace’s shared `ai_router/router-config.yaml`. That recreates the Round 4 failure for API-key-only teammates/fresh clones: they skip API-key validation and then fail on the intentionally ignored `copilot-catalog.lock`.
  - **Details:** This challenges the **Round 4 / L3 remediation**, not the settled fact that the tracked packaged config is now back to `api`. The violation is the new contract: `docs/clone-setup.md` says **“Do not put `transport.profile: copilot-cli` in `ai_router/router-config.yaml`”** and the remediation says the seat choice belongs in `ai_router/local-overrides.yaml`. But `tools/dabbler-ai-orchestration/src/utils/copilotSeatSetup.ts` still reads/writes `ai_router/router-config.yaml` on success (`renderTransportProfile(..., "copilot-cli")` then `writeConfigAtomically`), tells the operator it was “written to ai_router/router-config.yaml,” and even instructs manual repair by setting it in that file. `docs/concepts/tier-model.md` still documents the same old guided/manual behavior, and `copilotSeatSetup.test.ts` pins the rewrite as expected. The local override path is also not fully wired into the extension: `schemaValidator.ts` closes `local-overrides.yaml` with `additionalProperties: false` and has no `transport` property, so the config editor rejects the newly supported override.

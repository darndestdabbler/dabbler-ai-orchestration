Step 1 -- where the engine opens. One option in Tools > Options > Dabbler: in Visual Studio, or in Windows Terminal. It is this interface's own preference and no rule of the router's. A new install opens the engine in Visual Studio.

Step 2 -- every engine the extension starts. Start Session, Continue Session, a consult and a Mechanic each open as an Engine tab of their own in the editor area, titled as their Windows Terminal tab is today, through the host of session 369. Open Engine Here, the proving command, goes.

Step 3 -- when it cannot start. If the pane or the host fails before an engine exists, the extension says why in one sentence and opens the engine in Windows Terminal. If an engine for that session is already running, it attaches to that one: a session never has two.

Step 4 -- the session's row. Continue Session on a session whose engine is running brings its tab forward and starts nothing. A session that ends closes its tab and its engine, as the VS Code extension closes a finished session's terminal. Both are about the Engine tab of Step 2, whose engine runs through the host: an engine opened in Windows Terminal, by the option or as the fallback, is launched as it was before this session, and the extension neither finds nor closes it -- wt.exe hands back no tab or engine process, and has no command that focuses or closes a tab. (Amended with the operator's approval during the session, after the review read Step 4 as covering Windows Terminal engines too.)

Step 5 -- closing Visual Studio with an engine running. One sentence before it closes: the session carries on, and its tab is offered when the solution is opened again.

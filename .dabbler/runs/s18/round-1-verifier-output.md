ISSUES FOUND

- **Issue 1:** Bootstrap invents test commands from ecosystem markers that do not declare those commands, and nested-project detection emits commands from the wrong working directory.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/bootstrap.py, tests/test_bootstrap.py`
  - **Failure scenario:** A common repository containing `pyproject.toml` but using `unittest`/`nox`, a `package.json` without a working `test` script, a Gradle wrapper without globally installed `gradle`, or only `frontend/package.json` is bootstrapped. The generated `dabbler.yaml` respectively mandates `python -m pytest`, `npm test`, `gradle test`, or root-level `npm test`. Preverification and `final-full` then fail deterministically until a person repairs the generated declaration. This is probable because these markers and nested layouts are explicitly accepted by the detector, while none of the required runner declarations or working directories are validated.
  - **Acceptance criterion:** `JUDGMENT - For every supported marker, including markers found only below the repository root, bootstrap must either emit a test command demonstrably declared and runnable from the configured location or emit no suite, with tests covering missing scripts/runners and nested-only build files.`
  - **Details:** **Violation:** The session requires that “Nothing in project setup blocks on a human,” while the implementation itself claims detection records what “the repository already declares itself to be” and avoids guessed runners. **Impact:** Bootstrap can generate an unrunnable tracked configuration on its main path, blocking the lifecycle’s required preverification and full-suite stages and requiring manual correction; this materially defeats automated project setup and should block merge. **Evidence:** `ECOSYSTEMS` maps generic files such as `pyproject.toml`, `setup.py`, and `package.json` directly to fixed commands without inspecting test dependencies or scripts. It also recognizes `*/package.json`, `*/pom.xml`, and nested project files but emits commands with no corresponding working directory. `_suite_block` persists those guesses as authoritative suite declarations. The tests only prove that generated YAML parses; they never establish that the emitted command is declared or runnable. The correct behavior is to derive commands from explicit repository declarations at the correct location, or leave the suite undeclared.

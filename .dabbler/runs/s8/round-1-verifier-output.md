**ISSUES FOUND** Two blocking regressions remain: seat-backed verifier selection ignores model-level verifier eligibility, and `smoke.py` no longer tests provider APIs under the new default transport.

- **Issue 1:** Copilot verification can route to models the config explicitly marks as not trusted to verify.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/transports/copilot.py:1704-1730, ai_router/router-config.yaml:73-77, ai_router/router-config.yaml:105-107, ai_router/router-config.yaml:133-145, ai_router/selection.py:81-113`
  - **Failure scenario:** On the shipped `copilot-cli` path, every verification call excludes the author's provider. For OpenAI-authored work, the shipped verifier order puts `gemini-3.1-pro-preview` ahead of Anthropic, and `resolve_role_candidates()` will select it whenever the seat confirms it, even though the model record marks that same model `is_enabled_as_verifier: false`. That means a normal cross-provider verification round can make merge/block decisions with a model this repo explicitly says is not trusted to judge other models' work.
  - **Acceptance criterion:** `JUDGMENT - On the copilot-cli path, verifier selection must intersect the confirmed catalog with a transport-independent verifier-eligibility source, so a model record marked is_enabled_as_verifier: false cannot be chosen as a verifier.`
  - **Details:** **Violation:** the shipped config says `is_enabled_as_verifier` is “trusted to review another model's output” and “a property of the record rather than of a role,” but `resolve_role_candidates()` never consults model records and admits every confirmed catalog entry. **Impact:** verifier trust becomes transport-dependent, so a seat-backed review can be decided by a model the repo explicitly excludes from verifier duty. **Evidence:** `roles.verifier.prefer` names `gemini-3.1-pro-preview`, that model record sets `is_enabled_as_verifier: false`, the API path filters verifier candidates on that flag, and the Copilot path does not. **Correct answer:** apply verifier-eligibility filtering before ordering Copilot candidates, and keep the shipped verifier preferences consistent with that filter.

- **Issue 2:** `smoke.py` stopped exercising provider APIs after the default transport flipped to `copilot-cli`.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `smoke.py:1-2,14-33, ai_router/router-config.yaml:54-60, ai_router/config.py:317-340`
  - **Failure scenario:** A developer with both a Copilot seat and provider keys runs `smoke.py` to validate Anthropic/OpenAI/Google API access. Because the shipped config now defaults to `copilot-cli` and the script calls `route(...)` without a transport override, each probe runs through the seat instead of the provider API. A green `[ok] openai` or `[ok] google` now proves only that the seat could answer through that provider family, not that the direct API key/config works, so broken API setup is likely to slip through until a real API-backed workflow fails.
  - **Acceptance criterion:** `JUDGMENT - The probe calls in smoke.py must force the direct-API transport, so its per-provider smoke test still validates the configured provider API path even when the shipped profile is copilot-cli.`
  - **Details:** **Violation:** `smoke.py` promises “one real routed call per configured provider whose API key is present,” while `resolve_transport()` uses `transport.profile` when no override is passed and the shipped profile is now `copilot-cli`. **Impact:** the script's stated purpose is broken on the new default path; it can report success without ever touching the provider API being “smoked.” **Evidence:** `smoke.py` loads config, filters on API-key presence, then calls `route(...)` with no `transport="api"` override; the bundled config now ships `transport.profile: copilot-cli`; `resolve_transport()` honors that profile by default. **Correct answer:** hard-pin the smoke probes to the API transport instead of inheriting the new seat default.

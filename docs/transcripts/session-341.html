Why. The operator, 2026-11-14, on what the framework is for: a .NET or Java solution, or some other kind of programming solution, "or it could be a blog post, or novel, or policy document or legislation". The framework needs no built-in support for each, "but it shouldn't choke if a user elects to pursue a novel use case".

Session 1 as scaffolded today chokes on all of them but the first. It asks what "the solution" is, then how production is split and which part may talk to the database, and writes a plan of handoff artifacts, modules, and projects in a .sln or a pom.xml. Session 2 challenges the module cuts and plans a skeleton session that writes a solution file. A person writing a standard operating procedure is asked about an API tier.

So the first two sessions change character. Session 1 is about understanding the goal, in the person's own terms, and its questions are written out word for word so that every engine asks the same ones. Session 2 still challenges and decomposes, toward the aim the operator stated: a series of sessions that produces a draft of the whole work, or of a component of it, with planning for whatever is deferred. The .NET and Java scaffolding stays exactly as it is, and applies only when the goal is a new or rebuilt .NET or Java solution.

The questions live in session 1's own text in the scaffolded session-plan.md, and in PLAN_PROMPT, which is the same session run untracked. Not in AGENTS.md: that file is read at the start of every session for the life of the repository, and these are asked once.

What is scaffolded is kept short, because it is the part that cannot be taken back: sessions 1 and 2 are written into a repository once and stay as they were written, whatever a later release learns. So the scaffolded text carries what is common to every kind of work -- the questions, the brief, what a plan must hold -- and the guidance for one kind is printed by the router, which a release does update: dabbler bootstrap --print-plan-prompt and --print-decomposition-prompt, which exist today. The scaffolded session says to run the one that applies once the brief says what is being made. The .NET and Java text moves there whole. A long text with four branches is also where an authoring model goes wrong, asking a person writing a script about handoff artifacts.

Step 1 -- session 1, "Understand the goal and write the plan". The session reads the brief it was given, in the prompt or at docs/planning/brief.md, says back what it understands, and asks only for what the brief leaves open. With no brief it asks the first question, in these words:

> What are you making? Pick one or more, or say it in your own words. > > 1. Software: an application, a script, a library, a data analysis. > 2. A work document: a policy, legislation, a specification, a standard > operating procedure, a presentation, a research paper. > 3. A creative work: a story or a novel, a poem, a screenplay, a blog > post, a podcast episode, a song, a sermon or a lecture, a prayer. > 4. Something else. Say what.

and then the second:

> Tell me what you can about it now, and three things if you have them: > > - Who is it for, and what would make a first draft useful to them? > - Is there material to start from: a specification, documentation, a > plan, a draft, links to related works or ideas? Say where it is. > - What is already fixed: a deadline, a length, a form or a house style > it must follow? For software, a language, a platform or an > architecture already decided?

The categories are a prompt and not a boundary: a research paper with code in it is two of them, and the plan is shaped by what the person said, not by the number they picked.

Refinement is not asked about before the idea has been heard. When the person has answered, the session says back what it understood, names what is still open, and asks:

> Is this clear enough to plan a first draft, or shall we work on it > together first? Working on it first is usually worth it. We can stop > and carry on later: I keep what we have agreed, and what is still open, > in the brief.

Working on it is a conversation held in this session, across as many sittings as it takes: the session asks, proposes and is corrected, and writes nothing but the brief until the person says it is clear enough to plan. The answers go to docs/planning/brief.md with the kind of work on its first line, before any plan is written. The rule that the substance is the person's stays in the same words: no neighbouring directory is searched, and nothing is drafted from the folder's name.

Where the repository already holds a solution or a build file, the first question becomes a confirmation and names what was found: "This folder holds a Java application. Is that what we are working on?" The person may be writing its operating procedure.

Before it asks for material, and before it reads any, the session says where the work goes and waits for the person to say go on:

> Before you point me at any material: what you give me, and the drafts > made from it, are sent to [the authoring AI] and to [the reviewer], and > each session's work is committed and pushed to [the remote, or "no > remote: it stays on this machine"]. Is that all right for this > material? You can change either AI in the Configuration first.

The names are read from dabbler configuration explain and the remote from git. Round 25's plan made this a sentence that waited for nothing; three of the four advisors, and both of the stronger pair, said to wait. A file read in the same turn as the warning has already left the machine, and a policy draft is not a code sample. It is a question in a conversation that is already asking questions, not a gate in code: the framework does not judge the answer.

Material in .docx, .pptx or another binary format is not read as it is: the session asks the person to save it into the folder as text or Markdown first.

Step 2 -- the plan takes the shape of the work. docs/planning/solution-plan.md keeps its name and carries, for every kind: the objective a reader can act on (what it is for, who uses, reads or hears it, what it must do or cover, what is out of scope); the material it starts from; what is fixed; the parts, each with what it is responsible for; what this plan drafts and what it defers.

  • An application in .NET or Java: today's text, unchanged in what it asks and moved to the router's printed guidance -- the production split and its question, the handoff artifacts, the modules as projects reached by project reference.
  • Any other programming solution: the parts are that language's own units -- scripts, modules, packages -- and one is a fine answer. The production split is asked about only where the person says something runs separately; a script run by hand has no tiers. The plan says how the work is shown to run: the tests the language has, or the command that exercises it.
  • A work document or a creative work: the form (the kind of document or genre, its length, its structure, its voice, the house style or citation rule it follows); the parts as sections, chapters, scenes or slides; and how a draft is judged -- against the brief, against the source material, and against itself. The work is kept as text files a reviewer can read line by line, Markdown unless the person names another text format, written one sentence per line so that a changed sentence is a changed line. Which copy is the authoritative one is asked and agreed, not assumed: where the person's office already keeps the document in Word, with its comments, numbering and tracked changes, the session says plainly that this framework works on a text copy, that a Word copy is made from it by a person, and that changes made in Word come back only by a person bringing them into the text. An office that cannot work that way is told so, and is not told the framework fits.
  • Something else: the common list above, and the person's own words for the parts.

Step 3 -- session 2 breaks any of them down. It challenges the parts as it challenges modules now -- whether each should exist, and whether what it promises is something a reader or a test can check -- and breaks the plan into numbered sessions that together produce a draft of the whole work or of the component the plan names. Its own text stops calling a session "one AI coding session". Where the brief leaves questions open that a conversation, a piece of research or a trial would settle, it may plan those as the first numbered sessions, each ending in an amended brief, and a planning session after them that breaks down the rest: that is how a person gets more than one session of working the idea through, and no session is renumbered for it. What the plan defers is recorded in it; a planning session for the deferred work is written only where the person has said what comes next.

Every step still has a check the framework can run, and the text says what one is for prose, since the framework refuses a step without one: a command that exits 0 when the file exists and carries the sections the step was to write. Which command is what session 339 found to run on a locked-down machine. The text says what such a check proves and no more: the draft is there and has its sections.

The rest is a model's review, and the text bounds it. Each drafting session's section names the requirements it answers and the sources it must agree with, and says what counts as an error -- a requirement missed, a source contradicted, an earlier section contradicted, a stated rule broken -- and that wording, structure and taste the brief does not fix are suggestions. Nothing here says a draft was verified, or that it is good: a person reads it and decides, and the guidance says so.

The skeleton session, the suite it declares, the architecture test, the packaging session and the release sessions are planned where the plan names a .NET, Maven or Gradle solution, in today's words; another language gets a first session that writes its own build and declares its suite where it has either; a document or a creative work gets no skeleton, packaging or release, a suite only where something can be run over it, as session 339's documentation had, and its first drafting session writes prose, laying out the files as it goes.

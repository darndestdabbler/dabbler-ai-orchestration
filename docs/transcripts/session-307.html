Session 307 of 309: .NET Framework builds the way Visual Studio builds it

Scope: packages/router/src/bootstrap/detect.ts (the dotnet-framework suite), packages/router/src/checks.ts and packages/router/src/testEvidence.ts (the {msbuild} and {vstest} substitutions and the stop), packages/router/src/packaging.ts (the substitution it already does, shared), packages/router/src/affected.ts (narrowing by /TestCaseFilter), the tests named after each, docs/driving-a-session.md, README.md

Why. Session 305 recognises a non-SDK project and declares it with no command, which is honest and useless: a maintenance session on an ASP.NET MVC 5 application has no suite to run and no compile to prove. The way such a project builds is the way Visual Studio builds it -- MSBuild.exe from a Visual Studio or Build Tools installation, the .NET Framework targeting pack for its version, NuGet restoring packages.config, and vstest.console.exe over the test assembly -- and none of that is dotnet test. The pieces are findable: vswhere.exe sits at one fixed path on every machine with a Visual Studio installer, and answers where MSBuild and vstest are. On the machine this was planned on it answered Visual Studio Community 2026, MSBuild, vstest and targeting packs up to 4.8, and no 4.8.1 pack -- which the first borrowed repository targets, so the stop this session writes is one the walk will meet.

What. The dotnet-framework ecosystem gets its compile control and its suite, both spelled with two placeholders the framework fills from vswhere at spawn, and a stop that names what is missing.

Step 1 -- the suite and the control. For a repository whose graph holds a non-SDK project, detection declares a compile control of {msbuild} <solution> /t:Restore;Build /p:RestorePackagesConfig=true /p:Configuration=Debug /v:minimal /nologo, and a suite whose command is {vstest} <test assemblies> with /logger:console;verbosity=minimal, the assemblies read from each test project's AssemblyName and OutputPath (with the defaults MSBuild uses where they are absent). The test runner is read from the test project's packages: an xunit, NUnit or MSTest adapter runs under vstest; a runner vstest cannot drive -- Fixie 1 is one -- makes the suite the runner's own console from packages/, run whole, and the suite says so in its comment. Narrowing is /TestCaseFilter: over FullyQualifiedName~<class> joined with |, declared as select with the separator, in affected.ts's existing shape.

Step 2 -- the placeholders. {msbuild} and {vstest} are substituted per argv element at spawn, beside the {output} and {secret} substitution packaging.ts already does, by asking vswhere.exe at %ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe with -latest -products * -requires Microsoft.Component.MSBuild -find MSBuild\**\Bin\MSBuild.exe and -find Common7\IDE\CommonExtensions\Microsoft\TestWindow\vstest.console.exe. The answer is read once per run and recorded in the control's detail, so the record says which MSBuild built the evidence.

Step 3 -- the stop. A machine with no vswhere, no MSBuild or no vstest stops before the control runs, naming Visual Studio or the Build Tools with the "ASP.NET and web development" workload as what to install, and never substitutes dotnet test. A machine whose targeting packs under Reference Assemblies\Microsoft\Framework\.NETFramework do not include the project's TargetFrameworkVersion stops naming that version's Developer Pack. Both are session start stops under maintenance, read from the machine and never from a declaration, in the shape of the engine and vehicle stops that already exist. A non-Windows machine stops with one sentence: this project builds on Windows.

Step 4 -- the words. docs/driving-a-session.md says what a .NET Framework repository needs on the machine and how the framework finds it; the README's setup table gains the row.

Non-goals. Building .NET Framework anywhere but Windows, or in the container runner. Converting a project, a solution or packages.config to anything. Web Deploy, publish profiles or IIS. A Developer Command Prompt: the binaries are found, not a shell. A stored path to MSBuild.

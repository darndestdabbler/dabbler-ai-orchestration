Session 358 of 364: Visual Studio says when a session needs a person

Scope: tools/dabbler-visual-studio/ (notices, themes, the keyboard)

Why. A session runs for an hour without anyone. If a stop waits in a window nobody is looking at, the developer finds out by checking, and checking is the going back and forth this extension exists to remove.

Step 1 -- the notices. A session paused and an instruction overdue, as the Dabbler Terminal's stream names them, raise an information bar in Visual Studio's main window with the router's sentence and a button that shows the Work Explorer at that session. A session that closes raises one too: VS Code has none, and a developer working in another solution has no other way to know.

Step 2 -- once. Each is raised once for its event, and not again when Visual Studio is restarted.

Step 3 -- themes. The three windows take Visual Studio's light, dark and blue themes for their text, backgrounds and the terminal's tones.

Step 4 -- the keyboard. Every row and action is reachable without a mouse, and each window has a command a developer can bind a key to.

Non-goals. Sounds, Windows notifications, or anything outside Visual Studio. A setting for which notices to raise.

Tests. In the library: a notice object raises one notice, and the same object read again raises none.

Releasable. No.

Work Plan

Make Visual Studio say when a session needs a person. The library gains TerminalNotices, which reads each object dabbler terminal --follow --json prints and returns the notice it raises, if any. A paused or instruction-overdue notice object carries the router's own sentence as its message. A session-closed line raises a closed notice, but only for a session this following saw open first, so a close that happened long ago is not reported as news. Each notice gets a key: the repository, the session, and the stop and reason, or the instruction seq and its outstanding seconds. The key is written to a file of raised keys under the user's local application data, and a key already in that file raises nothing, whether it is read again or read by a new TerminalNotices after Visual Studio restarts. The extension gains a notice watcher. The package now loads in the background once a solution exists. The watcher follows the open solution's repository and keeps following a repository whose session is still open after the developer switches solutions, so its close still reaches them. Each notice becomes an information bar in Visual Studio's main window with the message and a Show in Work Explorer button. The button shows the Work Explorer and selects that session's row, through a new WorkExplorerTree.Reveal. The three windows take Visual Studio's light, dark and blue themes for selected rows, buttons and menus, as they already do for their text, backgrounds and the terminal's tones. Every row and action can be reached from the keyboard, including a row's actions through the context-menu key. Each window's command gets a canonical name a developer can bind a key to.

Notices

In the Visual Studio library, add TerminalNotices.cs. A TerminalNotice has a Kind (paused, instruction-overdue or session-closed), a Session (the session's label, or null where the stream has not named one) and a Message. TerminalNotices(repositoryRoot, raisedFile) has Read(json), which returns the notice that one line of dabbler terminal --follow --json raises, or null. A notice object of kind paused or instruction-overdue raises its own message. An instruction-overdue notice takes the session the stream last named, from a phase line's session field. A line with event session-closed raises a closed notice ('Dabbler: session NNN is closed.') only if this following has seen that session in a phase other than complete; a close it never saw open raises nothing. Every other line raises nothing, and so does a line that is not JSON, because the Dabbler Terminal window already says what it could not read. SessionOpen is true while a session this following saw open has not been seen closed. Each notice's key is the repository root plus its kind and session, plus the stop and reason for a pause, or the seq and outstanding seconds for an overdue instruction. A key is appended to raisedFile as the notice is raised, and a key already in raisedFile raises nothing. That holds when the same line is read again, and when a new TerminalNotices reads the line after a restart. Tests in TerminalNoticesTests.cs: Read raises one notice for a notice object, and the same object read again raises none, either by the same TerminalNotices or by a new one over the same file. A session-closed line raises a closed notice after a phase line that saw that session open, and none without one.

Reveal

In the Visual Studio library (WorkExplorerTree.cs), add WorkExplorerTree.Reveal(repositoryRoot, session). It finds the session row of that repository: the row id is session:<root>/<number>, the root is compared as a full path without regard to case or slash direction, and the session label is compared as a number. It expands the row's ancestors, selects the row and returns true, or returns false where the tree shows no such row. Tests in WorkExplorerTreeTests: Reveal selects and expands to session 2 of a document's repository when given a padded label, and returns false for a session the document does not hold.

Info bar

In the Visual Studio extension, add NoticeWatcher.cs. On a solution being opened or closed, and once the package has initialized, it follows the open solution's repository with RouterFollow over terminal --follow --json and its own TerminalNotices, using the raised-keys file %LOCALAPPDATA%\Dabbler\visual-studio-notices.txt. It keeps following an earlier repository while that repository's SessionOpen is true, and stops following a repository that is neither the open solution's nor open, both when the solution changes and after a closed notice. Each notice raised is shown on the main thread as an information bar in Visual Studio's main window (IVsInfoBarUIFactory, with the host taken from VSSPROPID_MainWindowInfoBarHost). The bar carries the notice's message, a warning icon for a pause or an overdue instruction and an information icon for a close, a close button, and a Show in Work Explorer button. The button shows the Work Explorer window, asks it to reveal the session through WorkExplorerTree.Reveal, and closes the bar. In DabblerPackage.cs, load the package in the background once a solution exists (ProvideAutoLoad on SolutionExists), so notices are raised after Visual Studio restarts without any Dabbler window being opened, and update its comment. Start the watcher there and add a ShowWorkExplorerAtAsync(root, session). In WorkExplorerWindow.cs, add the reveal it calls. If the tree has not yet been filled, the reveal waits for the next document.

Themes

Give the Work Explorer, Dabbler Terminal and Configuration windows Visual Studio's light, dark and blue themes beyond the text and backgrounds they already take. Selected rows, focused or not, use Visual Studio's tree-view selection brushes (TreeViewColors) in place of WPF's system highlight. Buttons (Set Up Dabbler in This Solution and the Configuration window's root actions) use Visual Studio's themed button style (VsResourceKeys.ButtonStyleKey). The context menus the rows open use the theme's menu colours. The terminal's tones keep choosing between the light and dark palettes by the brightness of the tool window background, which also puts the blue theme on the light palette, and are redrawn when the theme changes. Every brush is a DynamicResource, so a change of theme repaints the windows without reopening them.

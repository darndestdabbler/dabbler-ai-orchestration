ISSUES FOUND

- **Issue 1: The Marketplace surfaces promise an unconditional cross-provider block, while the same release documents an accepted same-provider fallback**
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `tools/dabbler-ai-orchestration/package.json`, `tools/dabbler-ai-orchestration/README.md`, `ai_router/CHANGELOG.md`
  - **Failure scenario:** Marketplace visitors are told that every close receives cross-provider verification and that a session blocks if no alternate provider is available. A Direct API user with only the orchestrator’s provider available instead receives the release’s documented qualified same-provider path. Because provider availability and configuration failures are ordinary and the extension explicitly advertises Direct API as a primary path, users can rely on an independence guarantee the release does not consistently enforce.
  - **Acceptance criterion:** `JUDGMENT - The Marketplace README and package description accurately disclose the qualified DIRECT_API same-provider fallback, or the release behavior is shown to block whenever no different-provider verifier exists; the three release surfaces must state one consistent contract.`
  - **Details:** **Violation:** The task requires that “the content of the commit about to be tagged is true” and permits the claim that “a session blocks rather than passing when no different-provider verifier exists.” The listing says every session is reviewed by a different provider, says unavailable cross-provider verification blocks, and `package.json` advertises “cross-provider verification that runs before every close.” **Impact:** Provider independence is a central adoption and compliance claim, not peripheral prose. Shipping contradictory behavior materially defeats the session’s truth-in-listing objective and can change whether a team installs the extension. **Evidence:** The folded Set 123 S2 entry states that a `DIRECT_API` project with no usable key outside the orchestrator’s provider “warns on stderr and proceeds with a same-provider verifier,” with the qualification carried into the verdict and accepted by the close machinery. The correct answer is to disclose that qualified exception everywhere or remove it from runtime behavior before making the unconditional claim.

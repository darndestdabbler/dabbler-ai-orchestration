## NITS

- **The pricing safety guard does not protect newly initialized OpenAI entries from an incomplete context schedule.** In `ai_router/pricing_proposal.py:970`, `not_comparable_entries` is used only when the current entry already contains a `max_input_tokens` tier. A new entry such as `gpt-5-6-luna` can therefore accept the parser’s flat short-context rate even though the parser also reports a long-context rate whose boundary is unknown. The resulting flat declaration makes `resolve_rates` price long prompts at the short rate. The normal router’s input cap makes this unlikely today, so this is non-blocking; the safer behavior would be to hold any entry when the page exposes an additional context rate that cannot be mapped.

- **Historical correction disclosures apply aggregate factors without filtering rows by correction date.** In `ai_router/cost_report.py:historical_correction_notes`, the text claims the factor applies only to rows before `corrected_on`, but `by_model` contains only an aggregate cost and no row dates. A later report containing both pre- and post-`2026-08-04` `gpt-5-5` or `gemini-3-1-pro` rows will multiply the entire aggregate, overstating the corrected amount. Current historical figures are unaffected because the supplied ledger predates the correction; row-level date-aware reconciliation would remove the residual.

- **The registry contains a stale call-count statement.** The GPT-5.6 family comment in `ai_router/router-config.yaml` says the old alias covered “245 calls and ~$49,” while `s4-cost-reconciliation.md` and the changelog report 254 rows and `$51.0383`. This can confuse an operator reconciling the registry against the published disclosure, but it does not affect runtime behavior.

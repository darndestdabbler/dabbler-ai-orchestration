**ISSUES FOUND**

- **Issue 1:** The DIRECT_API precondition is checked after dispatch-time config loading still requires every enabled provider key.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/__init__.py:292-300`, `ai_router/__init__.py:1184-1221`, `ai_router/config.py:129-159`, `ai_router/router-config.yaml:23-63`
  - **Failure scenario:** A typical default DIRECT_API checkout has Anthropic, Google, and OpenAI enabled, but the target degraded case has only the orchestrator provider key. `route()` calls `_init()` before `_direct_api_precondition()`, and `_init()` calls `load_config(..., require_api_keys=True)`, which raises on the first missing enabled-provider key. The warning-and-proceed path therefore never runs.
  - **Acceptance criterion:** `JUDGMENT - In a committed DIRECT_API project with only the orchestrator provider key present and at least one other enabled provider missing its key, session verification reaches the same-provider verifier path with a warning instead of failing during config/API-key validation.`
  - **Details:** Violation: the plan requires “Check the precondition and warn without blocking” and says “When that cannot be met, the session proceeds and the record says so.” Impact: the exact single-key DIRECT_API scenario remains blocked before the new precondition can act. Evidence: `_init()` precedes the precondition in `route()`, while config validation still requires every enabled provider key.

- **Issue 2:** `verify_session` still passes the orchestrator provider as an explicit exclusion, so the degraded route cannot select the same provider.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verify_session.py:2751-2786`, `ai_router/verify_session.py:2944-2960`, `ai_router/verify_session.py:3418-3459`, `ai_router/__init__.py:1220-1241`
  - **Failure scenario:** If config loading is made to pass, the normal CLI path still sets `exclude_providers = [identity.effective_provider]` and forwards it to `route()`. In the degraded case, `route()` removes only its internally derived exclusion, then unions the caller-supplied exclusion back in, so the orchestrator provider remains excluded and same-provider verification is still unavailable.
  - **Acceptance criterion:** `JUDGMENT - Through the real verify_session CLI path, a degraded committed DIRECT_API session must not pass an effective exclusion set that still excludes the orchestrator provider after route() has authorized the same-provider fallback.`
  - **Details:** Violation: the plan requires “same-provider verification is permitted” when the DIRECT_API precondition cannot be met. Impact: the primary sanctioned entrypoint cannot exercise the permission. Evidence: `verify_session` always forwards the provider exclusion, and `route()` preserves caller exclusions even after `_precondition.degraded`.

- **Issue 3:** The same-provider qualification is computed but never persisted to the metrics stamp row.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verification_stamp.py:155-183`, `ai_router/verification_stamp.py:762-805`, `ai_router/metrics.py:289-306`, `ai_router/verification_stamp.py:1158-1171`
  - **Failure scenario:** Once same-provider routing succeeds, `complete_stamp()` adds `verification_qualification`, but `metrics.record_call()` writes only fields listed in `STAMP_FIELDS`, which does not include that key. The close gate later reads the metrics row, sees a same-provider verifier without the required qualification, and rejects the row as “not cross-provider.”
  - **Acceptance criterion:** `python -c "exec(\"import json, os, sys, tempfile\nsys.path.insert(0, 'ai_router')\nfrom metrics import record_call\nfrom verification_stamp import complete_stamp\nwith tempfile.TemporaryDirectory() as d:\n    path = os.path.join(d, 'metrics.jsonl')\n    os.environ['AI_ROUTER_METRICS_PATH'] = path\n    stamp = complete_stamp({'orchestrator_effective_provider': 'anthropic'}, verifier_model='model', response_content='VERIFIED\\n', verifier_provider='anthropic')\n    record_call({'metrics': {'enabled': True}}, call_type='route', task_type='session-verification', model='model', provider='anthropic', tier=1, complexity_score=1, generation_params={}, input_tokens=1, output_tokens=1, cost_usd=0, elapsed_seconds=0, escalated=False, stop_reason='stop', session_set='set', session_number=1, stamp=stamp)\n    row = json.loads(open(path, encoding='utf-8').readline())\n    assert row.get('verification_qualification') == 'same-provider', row\")"`
  - **Acceptance expectation:** exit 0
  - **Details:** Violation: the diff claims “the metrics stamp row (`verification_qualification`)” carries the qualification, and the plan requires the qualification to travel with the verdict. Impact: even a successfully produced same-provider verdict cannot corroborate close, because the machine-checked record drops the only field that makes it valid. Evidence: `STAMP_FIELDS` omits the new key, `record_call()` persists only `STAMP_FIELDS`, and `validate_stamped_row()` requires the key for same-provider rows.

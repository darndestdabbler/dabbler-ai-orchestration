**ISSUES FOUND**

- **Issue 1:** The environment-default branch reports a resolved verify type, but `load_config()` derives a different `transport.profile`.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verify_type.py:235-243`, `ai_router/verify_type.py:282-291`, `ai_router/verify_type.py:310-352`, `ai_router/config.py:196-207`, `ai_router/__init__.py:248-256`, `ai_router/tests/test_verify_type_resolution.py:259-271`
  - **Failure scenario:** A fresh Copilot-seat project has no `project-verify-type.txt` but does have `AI_ORCHESTRATION_VERIFY_TYPE=COPILOT_CLI`. `resolve_verify_type()` says the project is resolved as `COPILOT_CLI` with `transport_profile == "copilot-cli"`, while dispatch loads config as `"api"` and can fail on missing provider API keys. This is probable because that no-file environment branch is one of the required startup paths, and keyless Copilot seats are explicitly supported.
  - **Acceptance criterion:** `JUDGMENT - In the no-project-file environment-default branch, a reviewer must not be able to observe resolve_verify_type(...).transport_profile disagreeing with load_config(...)[\"transport\"][\"profile\"]; either config derives from that branch or the resolver no longer reports the unconfirmed environment suggestion as resolved.`
  - **Details:** **Violation:** the spec requires “Derive `transport.profile` from the resolved type” and ends with “`transport.profile` cannot disagree with it.” **Impact:** this ships the split-brain configuration class the session is meant to remove. **Evidence:** the resolver marks any non-`None` verify type as resolved and maps the env value to `copilot-cli`, but `derive_transport_profile()` deliberately ignores the env branch and falls back to config/default.

- **Issue 2:** `--confirm` / `--set` write `project-verify-type.txt` to the invocation directory, not the repository/project root.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/verify_type.py:147-180`, `ai_router/verify_type.py:196-221`, `ai_router/verify_type.py:460-487`, `docs/session-sets/123-verify-type-and-startup-simplification/spec.md:110-129`
  - **Failure scenario:** A user runs `python -m ai_router.verify_type --confirm` from a nested directory. The command exits successfully and writes `nested/project-verify-type.txt`; resolving from the repo root still finds no project file, so future sessions can prompt again or derive a different profile depending on cwd. This is probable because developers commonly run tooling from subdirectories and the resolver explicitly supports walking upward from nested directories.
  - **Acceptance criterion:** `python -c "exec('import os\nimport subprocess\nimport sys\nimport tempfile\nfrom pathlib import Path\nscript = Path.cwd() / \"ai_router\" / \"verify_type.py\"\nrepo = Path(tempfile.mkdtemp()) / \"repo\"\nnested = repo / \"a\" / \"b\"\nnested.mkdir(parents=True)\n(repo / \".git\").mkdir()\nenv = dict(os.environ, AI_ORCHESTRATION_VERIFY_TYPE=\"DIRECT_API\")\nsubprocess.run([sys.executable, str(script), \"--confirm\"], cwd=nested, env=env, check=True, stdout=subprocess.DEVNULL)\nassert (repo / \"project-verify-type.txt\").is_file()\nassert not (nested / \"project-verify-type.txt\").exists()')"`
  - **Acceptance expectation:** exit 0
  - **Details:** **Violation:** branch 2 must be “confirmed once and written to the file,” and the file is the project-root source of truth. **Impact:** setup can appear complete while producing a cwd-local answer instead of a project answer. **Evidence:** `main()` sets `root = Path.cwd()` and passes that directly to `write_project_verify_type()`; no repository-root normalization is performed.

- **Issue 3:** `load_config(path)` searches for `project-verify-type.txt` from process cwd, so an explicit config path can ignore the project file beside that config.
  - **Category:** Correctness
  - **Severity:** Major
  - **Evidence paths:** `ai_router/config.py:162-207`, `ai_router/verify_type.py:310-352`, `ai_router/guidance_report.py:642-654`, `ai_router/__init__.py:248-256`
  - **Failure scenario:** Automation sets `AI_ROUTER_CONFIG` or passes an explicit config path for a project whose root contains `project-verify-type.txt=COPILOT_CLI`, but runs from outside that repo. `load_config()` does not search from the config’s project, misses the file, keeps `transport.profile: api`, and dispatch can fail on a keyless Copilot seat. This is probable because explicit/env config paths are supported entry points, and existing tooling intentionally loads config by path so it can work from any cwd.
  - **Acceptance criterion:** `python -c "exec('import sys\nimport tempfile\nfrom pathlib import Path\nsys.path.insert(0, str(Path.cwd() / \"ai_router\"))\nimport config\nrepo = Path(tempfile.mkdtemp()) / \"repo\"\nrepo.mkdir()\n(repo / \".git\").mkdir()\n(repo / \"project-verify-type.txt\").write_text(\"COPILOT_CLI\\n\", encoding=\"utf-8\")\n(repo / \"router-config.yaml\").write_text(\"providers: {}\\nmodels: {}\\nrouting:\\n  tier_assignments: {}\\ntransport:\\n  profile: api\\ntransports:\\n  copilot-cli:\\n    lockfile: ai_router/copilot-catalog.lock\\n    roles: {}\\n\", encoding=\"utf-8\")\nprofile = config.load_config(str(repo / \"router-config.yaml\"))[\"transport\"][\"profile\"]\nassert profile == \"copilot-cli\"')"`
  - **Acceptance expectation:** exit 0
  - **Details:** **Violation:** “The file wins silently over the environment” and `project-verify-type.txt` is the “SINGLE SOURCE OF TRUTH.” **Impact:** a committed project answer can be silently ignored on supported explicit-path loads. **Evidence:** `load_config()` calls `derive_transport_profile(config)` without passing a start rooted at `config_path`, and `derive_transport_profile()` defaults its search to cwd.

ISSUES FOUND

- **Issue 1: Implementation-specific test counts are incorrectly defined as mandatory finish lines**
  - **Category:** Correctness
  - **Severity:** Major
  - **Failure scenario:** A typical reader’s independently generated implementation has a different test decomposition from the answer key—for example, 28 converter tests instead of 31, all passing with the required HTTP behavior. The tutorial would nevertheless tell them they have not reached Part A’s finish line. This is probable because the outline explicitly says the reader’s AI “will not produce the answer key’s code,” while test counts depend directly on implementation and test decomposition.
  - **Details:** **Violation:** The outline requires independently built versions, yet defines the finish lines as “**31 tests green**,” “**24 tests green**,” and “**74 tests green** overall,” and instructs Session 2 to quote “**12 tests, 97 ms**.” **Impact:** Correct implementations can appear incomplete, causing readers to chase arbitrary answer-key counts or preventing clean stopping between parts—the stated purpose of the finish lines. This would materially weaken the tutorial’s independent-build objective and should block merging the outline as Session 2’s authority. **Evidence:** `s1-walk-outline.md` §2 contains the exact counts while Part A states, “the reader’s AI session will not produce the answer key’s code, and that is fine.” **Fix:** Define finish lines behaviorally: all tests produced by that implementation pass, the relevant contract exchange succeeds, and the observable persistence/pipeline result is demonstrated. Label counts and timings only as answer-key observations, never acceptance criteria.

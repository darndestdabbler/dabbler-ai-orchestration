ISSUES FOUND

**Issue 1:** The evaluator counts supplementary recordings toward the ten-clean-run bar without evaluating those recordings against the per-run criteria
- **Category:** False Positive
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/os-capture-verdict.js`, `tools/dabbler-ai-orchestration/scripts/measure-os-capture.js`, `docs/session-sets/113-narrated-video-walkthroughs/s4-pilot-criteria.json`, `docs/session-sets/113-narrated-video-walkthroughs/s4-os-capture-measurement.json`, `docs/session-sets/113-narrated-video-walkthroughs/s4-os-capture-outcome.md`
- **Failure scenario:** The intended pilot path always contaminates primary run 1 by repointing its live recording at the decoy, leaving only nine clean primary recordings. The explicitly provided `--supplementary-run` path then supplies the tenth. However, C1–C4 are evaluated only over `measurement.runs`, while `cleanRuns` includes `measurement.supplementaryRuns`. A supplementary recording with wrong-window correlation, leaked occluder pixels, bad dimensions, or invalid caption timing still counts as clean whenever it completed all steps and produced a nonempty video. This bypass is certain on the designed supplementary path, and it can cause the authoritative evaluator to report `PASS` after the currently unmet criteria are resolved or waived even though one of the ten qualifying recordings failed the fixed per-run bar.
- **Acceptance criterion:** JUDGMENT - The evaluator must select one ordered set of ten qualifying clean recordings and apply every `bar.allOfPerRun` criterion to that same set; a supplementary recording with a failing C1, C2, C3, or C4 observation must prevent `barRunsMet` and the overall verdict from passing.
- **Details:** **Violation:** The fixed criteria require `"allOfPerRun": ["C1", "C2", "C3", "C4"]` for ten consecutive clean captures, while the outcome claims that the pure evaluator computes the verdict from those criteria. **Impact:** The operator can receive a machine `PASS` for a population different from the population actually evaluated, undermining the measured gate that determines whether capture may ship. **Evidence:** `evaluate()` builds every C1–C4 input exclusively from `measurement.runs`, then separately computes `cleanRuns` from `runs.concat(measurement.supplementaryRuns || [])`; `isClean()` checks only usability, completed-step count, nonzero video size, and control contamination. The committed measurement reaches ten clean runs using its supplementary run, and `measure-os-capture.js` documents that this supplementary path exists specifically to replace the contaminated primary recording. The correct fix is to evaluate the same qualifying run objects used by the bar, or to collect ten uncontaminated primary runs and keep controls wholly separate.

Why. Some of the operator's developers work in Visual Studio and need it: .NET Framework MVC is debugged under IIS Express there, with designers and a project system VS Code does not have. Consult round 29 (docs/design/consults/round29-synthesis.md) and the scope that followed (docs/design/visual-studio-extension-scope.md) came to a Dabbler extension for Visual Studio, and the operator approved it on 2026-11-17 with these decisions, which hold for sessions 343 to 362:

  • **It is built on master, in a folder of its own, and is not published until session 360's walk says it works.** That publication is the merge. If it is given up, one session deletes the folder.
  • The router computes and each interface renders. What a person sees is decided today inside the VS Code extension, in code that does not use VS Code. It moves into the router, the router prints it, and the VS Code extension reads it there. That is sessions 343 to 347, and each is worth having with no Visual Studio extension at all: a person at a bare terminal gets the same views, and so would any other editor.
  • The engine runs in Windows Terminal, beside Visual Studio, not in it. There is no chat pane.
  • Node is a prerequisite a developer installs, as the engine CLIs are.
  • Left out: the repositories and modules of the Solution Explorer, Set Up New Project, cloning and creating repositories, the solution workspace file, the troubleshooter and the walkthrough.

This session moves the first of the four parts. The Dabbler Terminal reads the records of a run under .dabbler/runs/ every half second and turns them into lines. It takes no input from a person. Of its 2,285 lines about a dozen touch VS Code, and all of it sits in the extension, where no other interface can reach it.

Step 1 -- the move. The record readers, the formatting and the polling state machine move from dabblerTerminal.ts to packages/router/src/views/terminalLines.ts, as a class that is given a width, a theme (light or dark) and a place to write, and knows nothing of any editor. What stays in the extension is the VS Code terminal around it: creating it, where it opens, revealing it when a session starts, passing on its size and the colour theme.

Step 2 -- the verb. dabbler terminal --sessions-dir <dir> prints the lines of the run in flight, or of the last one, and exits. --follow keeps printing as the run goes on, until it is interrupted. --width and --theme say how to lay the lines out; the defaults are the terminal's own width and dark.

Step 3 -- the lines as data. --json prints one JSON object per line in place of coloured text: the time, the event, its fields, and for each piece of text the tone the router gives it, by name. A job's own output, which the terminal passes through as it is, is one object per line of it. The two notices the terminal raises today, a session paused and an instruction overdue, are objects of their own kind in the same stream, so an interface that shows a notice reads it there and decides nothing.

Step 4 -- the extension reads it. The VS Code terminal is fed by the moved class, called in-process as the rest of the router is, and shows what it showed before, byte for byte. Its two warnings come from the notices of step 3.

Non-goals. Any change to what a line says, its colours or its layout. A terminal a person types into. A verb that draws a dashboard or redraws in place. The Work Explorer, Configuration or the engine: sessions 344 to

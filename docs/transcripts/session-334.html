Ahead of the walks, and first of three. The operator, 2026-11-16: staff are meeting stops that end in a rollback. An investigation of one staff repository (docs/syndromic-surveillance-v2-session-138-140-141-investigation.md, written against router 3.29.0) traced five of its sessions to one cause, and the cause was confirmed in this tree before this was planned. Sessions 334 to 336 ship together as 3.35.0, ahead of sessions 338 to 341: this one removes the cause, session 335 makes the plan a session is held to one reading, and session 336 lets a person report the stop they roll back from.

Why. A session can be declared from another session's work plan, and once it is, only a rollback undoes it:

  • planAsk tells the engine to write its plan to a file "for example .dabbler/scratch/plan.json". .dabbler/ is ignored and nothing empties it, so the last session's file is still there.
  • An engine's tool for creating a file refuses one that exists. The engine that does not notice runs the answer command anyway, and report reads the old file.
  • The same instruction forbids session_number in the file, so nothing in the file says whose it is. stampAnswer stamps this session's number on it, and the declaration goes on the activity log, which is append-only.
  • plan amend changes one step's files or checks and nothing else, and a cancel followed by a restore brings the same declaration back. In the staff repository this cost a rollback in sessions 119, 120, 138, 140 and 141, and a hand-written warning pasted into the plan in between.
  • A dispositions answer travels by file the same way and has the same gap.

Step 1 -- the instruction names a file of this session's own. The plan ask names .dabbler/scratch/plan-s<N>.json, and the dispositions ask names one that carries the session and the round. Still an example: an engine may write its answer anywhere outside the ledger.

Step 2 -- an answer says whose it is. The plan ask stops forbidding session_number and asks for it, and the dispositions ask asks for session_number and round. report refuses an answer file that carries none, in words that say what to add; one that carries another session's or another round's is already refused by stampAnswer, and that rule is unchanged. This is the guard that does not depend on the name, and it reads no clock. schema_version and recorded_at stay the framework's to stamp.

Step 3 -- an accepted answer is used once. Once an answer has been validated and written into the ledger, its file is removed where it lies under .dabbler/scratch/, resolved so that a link out of that folder is not followed. A refused answer's file stays, to be corrected. A file anywhere else is the engine's own and is left. A removal that fails is said in a line and does not fail the answer, which is already written.

Step 4 -- the plan ask says a check changes nothing. One sentence where the ask describes checks: a check that writes a tracked file is refused, so a generator is run as the step's work and the check proves its output is current. Session 138 of the staff repository learned it from two refusals.

Non-goals. Replacing a work plan once it is declared: a rollback before any step is accepted discards nothing that was committed, and it stays the way out until this release has run on staff machines and shown whether another is wanted. Comparing an answer file's modification time with the time its instruction was issued: round 27 found it refuses a good answer where two clocks disagree or a timestamp is coarse, and passes a stale one that was merely copied, and step 2 does its work without a clock. Proving a plan's content is the right one: a file written now for this session with the wrong steps in it is the reviewer's to catch, as it was in the staff repository. Emptying .dabbler/scratch/ at a start. What restore brings back. version.json: session 336 stamps it.

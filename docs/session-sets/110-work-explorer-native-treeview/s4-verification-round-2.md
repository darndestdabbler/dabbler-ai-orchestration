**ISSUES FOUND**

**Issue 1:** The staged release uses an invalid VS Code view-container icon shape, so the Dabbler activity-bar container is rejected.
- **Category:** Correctness
- **Severity:** Major
- **Failure scenario:** On a normal install of `0.49.0`, VS Code reads `contributes.viewsContainers.activitybar[0].icon` as an object instead of a string. VS Code rejects that custom container and falls the contributed views back to Explorer, so the operator/user no longer gets the Dabbler activity-bar container that the release claims and the UAT fix was meant to repair.
- **Details:** Violation: the release claims “The activity-bar icon is legible on light themes” and “the activity-bar icon contributes a light/dark pair,” but VS Code’s `viewsContainers` schema/handler requires `icon: string` and explicitly errors when `typeof descriptor.icon !== 'string'`. Impact: this changes the merge/release decision because the extension’s primary contributed container is not registered as shipped. Evidence: `tools/dabbler-ai-orchestration/package.json:49-52` sets `"icon": { "light": ..., "dark": ... }`; the same invalid shape is packaged in the VSIX and `verify_vsix_claims.py:77-82` incorrectly treats that object as a passing claim. The correct fix is to use a valid string container icon path/codicon, update the verifier to reject the illegal object shape, and rerun the relevant Extension Host/Layer 3 coverage after the manifest change.

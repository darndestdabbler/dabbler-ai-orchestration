- **Issue 1:** Ordinal fallback can still let an inserted step overwrite an unfinished seeded row when logged keys do not exactly match seeded keys.
  - **Category:** Correctness
  - **Severity:** Major
  - **Failure scenario:** A session plan is edited mid-flight to insert a new step before unfinished planned work. The orchestrator follows the documented convention and logs with the spec’s current step numbers, but uses its ordinary progress/log keys rather than the seeder’s generated slug. The inserted step claims the old row by number, the shifted real step claims the next planned row by number, and the originally unfinished planned row disappears instead of remaining visible `[ ]`. This is probable because the constitution still instructs logging with the spec’s step numbers, while exact seeded `stepKey` reuse is not made the operator-facing convention.
  - **Acceptance criterion:** `JUDGMENT - In a seeded plan, after a mid-flight insertion, a logged row with a non-empty stepKey that does not match any seeded planned step must not ordinal-claim and replace a different planned row; unfinished original planned rows remain visible pending.`
  - **Details:** **Violation:** The spec requires “a planned step never executed must remain visibly `[ ]`” and the L3 fix claims identity-before-ordinal stops insertion cascades. **Impact:** The checklist can still hide unfinished planned work in the named messy case, so the remediation does not satisfy the merge-blocking finding. **Evidence:** `_reconcile` first tries key claims, but then every unclaimed logged step still falls back to `_claim(by_number, _step_number_of(entry), position)`, and claimed rows replace `plan_rows[target]`. With seeded steps `register/build-the-thing/verify-it`, logged rows `(1, register)`, `(2, new-work)`, `(3, build)` produce only logged rows for register/new-work/build; the pending `verify-it` row is gone.

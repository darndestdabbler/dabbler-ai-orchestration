The operator, 2026-11-16, watching session 334: "Between the framework output and the AI output, we shouldn't leave human operators wondering what is going on." Step 2 of that session sat for more than half an hour with the terminal's last line waiting-on says=Author owes step answer-says-whose - 0:01, though the answer had been given and the framework was running its checks. The operator asked whether it was stuck, and the only way to tell was to list the machine's processes. It ships with sessions 334 to 336 as 3.35.0.

Why. Two silences, both measured in that session:

  • An answer arriving says nothing. The event log has run-resumed and nothing more until the checks end, and the waiting record still names the author, so the terminal goes on saying the author owes an answer the author has given.
  • A step's checks are logged only once all of them have run. runStepChecks runs every check and then the loop logs each result, so a step whose checks take twenty minutes prints nothing for twenty minutes and then everything at once. Nothing is logged when a check starts, and the named tests after it are the same.

Step 1 -- an answer says it has arrived. When the driver takes up an answer from the author -- a plan, a step's report, a round's dispositions -- it logs one line before judging it: what was answered (the step's id, or the round), its status, and its notes. The waiting record moves off the author at the same moment, to the framework's own work, so the waiting-on line says what the framework is doing rather than what the author owes. The answers the framework already logs when they arrive -- a verdict, an adjudication, the Mechanic's -- are confirmed to have a line each, and one that has none gets one.

Step 2 -- each check says when it starts and when it ends. A step's checks are logged one by one: a line as each starts, naming its argv, and a line as each ends, passed or failed, with how long it took. The named tests after them are logged the same way. While a check is running, the waiting record names it, so the waiting-on line reads like a job's, with the check and the time it has run against its time limit.

Step 3 -- a long list of test files reports progress. suite.mjs runs a list of test files in batches rather than in one node --test call, and prints one line as each batch ends: how many files of how many are done, and how many tests passed and failed so far. The batches run one after another, so a run takes somewhat longer; the operator prefers progress that costs a little time to speed that says nothing. A failure is still reported once, at the end, with the whole output it has today.

Step 4 -- the terminal renders them. The Dabbler Terminal shows the new lines in the format it uses for every other line (hh:mm:ss, the event, its fields, a hanging indent). Nothing from a check's or a batch's own output is copied into the terminal: what a person reads is that it started, that it is still running, and how it ended.

Step 5 -- the other quiet stretches. Read the driver for any other place where the framework starts work and logs nothing until it ends, and give each one a line as it starts. Anything found that is larger than a line is written into this plan as a session of its own, not done here. The changelog's 3.35.0 section gains a paragraph saying what a person now sees.

Non-goals. Copying a check's, a test's or a job's output into the terminal: the job's log already holds it and is named. A progress bar or any other widget. Changing what a check, a test run or a job decides, or any time limit. Running batches in parallel, which would put back the silence this session removes. Breaking a single test file into pieces: a batch is a group of whole files. version.json: session 336 stamps 3.35.0, and this session changes no version.

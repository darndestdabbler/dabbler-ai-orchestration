Session 319 of 322: The guide says what holds an AI to the rules

Scope: docs/guide/discipline.md, docs/guide/verification.md and docs/guide/the-record.md (new), docs/guide/README.md (new: the index), packages/router/scripts/check-shipped-docs.mjs (the pages it reads)

Why. The operator, 2026-11-11: the two front pages undersell the product and no longer describe it, and the message a stranger should take away is discipline. An AI works inside well-defined rules. A model from a different provider must review the work. The framework runs the tests and hashes the code, so an AI cannot easily claim work it did not do. Every deterministic job is the framework's. The record is open to anyone who clones the repository.

The operator added a second message the same day: the framework standardizes the work of AI. Every session is planned, run and recorded the same way whichever model writes it, so a person or a later model can pick the work up where the last session finished, the next day or the next year, from what is in the repository.

Every one of those is true, and none has a page that says how. The mechanisms are spread through docs/driving-a-session.md, which is 1,700 lines written for someone already driving a session, and through a root README that is half reference manual. A front page can make a claim in one sentence only if it can link to the page that proves it. Sessions 319 and 320 write those pages; 321 rewrites the two front pages over them, with the operator's screenshots; 322 releases.

What. Three pages under docs/guide/, each written for a developer or a manager deciding whether to trust the product, who has not run a session. Each claim is followed by its mechanism and the command or file where a reader can see it for themselves. Each page is short enough to read in one sitting and links to driving-a-session.md for the full account instead of repeating it.

**Step 1 -- discipline.md: the rules, and what enforces each.** One instruction at a time, and the instruction in hand is the whole of what is asked. Each step declares its files and its checks before work starts. The framework hashes the working tree (SHA-256 over every tracked path and its content) before and after a step's checks, and refuses a report over a tree that moved. The approved plan carries a digest bound in at approval. The test run of record is held to the digest of the tree it ran against, so a change after the run makes it stale. The gates at the close, each with what it reads. The verbs that are a person's and refused to an engine: cancel, rollback, close, session waive. Then the list of what the framework does so that no AI has to be trusted to: registration, progress, each step's checks, the tests, the review rounds, the commit, the push and the close.

**Step 2 -- verification.md: two models from different providers.** Who the Primary Reviewer is and why it is never the author. What it is sent. Round 1 over the whole diff and later rounds over the fix. Findings answered and fixed without a person, round after round up to the cap. A dispute with evidence, and the Auxiliary Reviewer that settles one. The two ends at the cap. verify reopen. The raw reviewer output kept before any parsing. No verdict a person can type.

**Step 3 -- the-record.md: what is written down, and where.** The plan, the activity log, the change log, the decisions log and the work plan under the sessions root, with who writes each. The run records under .dabbler/runs/. The transcript page committed for every session under docs/transcripts/, with one linked as an example. dabbler status and dabbler transcript. What session waive leaves on the record.

The page ends with a section headed *Picking the work up*, which is the operator's second message and the reason the record has one shape. Every session has the same phases and leaves the same files, whichever engine and model wrote it. Every engine reads the same instructions, from AGENTS.md. A session starts in a fresh conversation and is handed its instruction by the framework, so nothing it needs is in an earlier chat or in one model's memory. The section then lists what a person or a model new to the repository reads, in order: the plan for what is next, dabbler status for where things stand, the last session's transcript for what was done and what the reviewer said, and the decisions log for why. Each sentence is checked against the running product before it is written.

Step 4 -- the index and the check. docs/guide/README.md lists the pages with one line each. check-shipped-docs.mjs reads every page under docs/guide/, so a guide page cannot name something the product has retired.

Non-goals. Rewriting driving-a-session.md or quick-start.md. A claim with no mechanism beside it. A stronger claim about tests than the mechanism: the framework runs the automated tests before any code is committed; the reviewer is shown every changed file with no test named after it and asked to judge whether it is tested; a test the session's plan promised and did not deliver is a blocking finding, and any other missing case is advice. The page says exactly that. A claim that any model can continue any repository: the claim is about the record, which needs no particular model to read it, and a seat that does not list the model a repository selected is still refused at the start. Decision ids, session numbers or incident history on a guide page. Any change to behaviour.

Tests. None added: these are pages. The lint control runs check-shipped-docs.mjs over the new pages, and each step's check is that run.

Releasable. Yes -- with 320 and 321, as 3.32.3 in session 322.

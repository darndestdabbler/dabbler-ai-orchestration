Session 299 of 300: An engine terminal ends with its session

Scope: tools/dabbler-ai-orchestration/src/commands/sessionCommands.ts (the createTerminal call and Start), the extension's sessions watcher, the extension manifest (one new setting), their tests; version.json and the manifests npm run stamp:version writes; tools/dabbler-ai-orchestration/CHANGELOG.md

Why. Staff reported that Dabbler starts slowly. On 2026-11-03 the operator's machine had 63 claude.exe processes holding 15 GB. 54 of them were started by Start Session ("Run dabbler session next …") and went back as far as 2026-10-22. Memory commit stood at 115.9 of 118.2 GB, and every process start took seconds, including bare node -e 0 and git --version. Dabbler 3.27.0 and 3.28.0 timed the same, so this is not a regression.

The cause is that Start opens a terminal whose shell *is* the engine CLI (shellPath: claude or copilot, with -i for Copilot), and nothing ever closes it. Each session leaves one idle engine process until someone closes the tab. The Copilot seat is affected exactly as Claude Code is. The -p calls a reviewer or Mechanic makes exit by themselves.

The terminals are also created without isTransient. Under VS Code's default terminal.integrated.persistentSessionReviveProcess (onExit), a terminal that persisted is recreated when the workspace reopens, which for these terminals means re-running the engine with its opening sentence. The operator's machine sets that option to never, so its leftover processes were never revived; most machines keep the default.

Step 1 -- Dabbler remembers the terminals it opens. Start remembers each terminal it opens, together with the repository root and the session number it registered. That covers only terminals Dabbler opened, never one the person opened. A remembered terminal is *finished* once the sessions watcher sees its session reach complete or cancelled. A terminal the person has already closed is forgotten without a word.

Step 2 -- at most N finished terminals stay open. A new setting, dabbler.keepFinishedSessionTerminals, defaults to 2 and has a minimum of

  1. So the current session's terminal plus two finished ones may be open, and a fourth closes the oldest. Dabbler applies the limit across the window at two moments: at Start, before the new terminal opens, and when a session closes.
  • When the finished terminals exceed the limit, the oldest are disposed first. That ends their engine processes, and the session that just finished stays open.
  • 0 closes a terminal as soon as its session closes. A large value effectively turns cleanup off.
  • A terminal whose session is still in progress never counts and is never closed.
  • When anything was closed, Dabbler shows one *information* toast (showInformationMessage, never a warning or an error) naming the sessions, such as "Closed 1 earlier session terminal (session 12) to free memory." It carries one button, "Change limit", which opens the setting. There is no prompt and no question asked.

The new terminal never depends on an old one: no parentTerminal, no reused position, no reused process. So a person closing an old tab at any moment, before, during or after the check, changes nothing. Disposing an already closed terminal is a no-op, and Start opens the new terminal either way.

Step 3 -- engine terminals do not outlive a reload. The engine terminal is created with isTransient: true, so VS Code neither persists nor revives it, whatever persistentSessionReviveProcess says. The CHANGELOG 3.29.0 section says what changed for a developer and the new setting. Bump version.json to 3.29.0 (a minor: new behaviour and a setting), and stamp it with npm run stamp:version.

Non-goals.

  • A prompt or question when a session closes.
  • Reusing a terminal's process or position.
  • Sending /clear or any keystrokes into an engine.
  • A cleanup command, or counts in Troubleshoot.
  • Killing engine processes Dabbler did not start.
  • Changing the unattended session drive.

Tests.

  • In the extension's unit suite (mocha, with src/test/vscode-stub.js):
  • with the default limit, a fourth finished terminal closes the oldest, and the toast is an information message naming it;
  • a limit of 0 closes a terminal when its session closes;
  • nothing closes, and no toast appears, while the count is within the limit;
  • in-progress terminals and the person's own terminals are never disposed;
  • a terminal the person disposed before or during the check produces no error, and the new terminal still opens;
  • the terminal options carry isTransient: true.
  • npm run check:version checks the stamp.
  • The walk, from the installed VSIX on a scratch repository, recorded in docs/driving-a-session.md:
  1. Run four sessions to their close with the default limit: after the fourth, the first session's terminal closes, an information toast names it, and its engine process is gone from Task Manager.
  2. Set the limit to 0 through "Change limit": the next session's terminal closes when that session closes.
  3. Close an old terminal by hand just as Start is chosen: the new one opens with no error.
  4. Reload the window with persistentSessionReviveProcess at its default: no engine terminal comes back.

Releasable. Yes -- as 3.29.0 in session 300.

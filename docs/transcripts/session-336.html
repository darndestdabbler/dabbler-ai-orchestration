Ahead of the walks, and last of three. The operator, 2026-11-16: staff are starting to meet framework stops that end in a rollback, and those are the stops the maintainers most need to hear about. Sessions 334 and 335 remove the cause that was found; this one is for the next cause, which nobody has found yet. It ships with them as 3.35.0.

Why. A stop a person rolls back from is one the framework gave no acceptable way past, and today it is the one stop that cannot be reported:

  • Report this stop to Dabbler is offered only while a stop stands over the session in flight (hasStandingStop). After a rollback nothing is in flight, so the item is gone.
  • rollback moves the run record of every session it undoes to .dabbler/superseded-runs/, and defect-report --session N reads the live record only, so it refuses: the session "met no stop the framework recorded".
  • The Mechanic's two lines for the maintainers are read from mechanic-log.md, a tracked file the rollback's reset or revert takes back with everything else.
  • So the report can be written only before the rollback, and nothing in the rollback's one dialog says so.

Step 1 -- the dialog offers it. Where the session in flight stands at a stop, the rollback's modal carries a third choice, "Report, Then Roll Back", and its detail says the choice is one provider call and that nothing is sent to the maintainers. It is still one dialog: nothing is asked between the choice and the rollback. The report is written first, by the same defect-report call Report this stop makes; then the rollback runs, bound to the HEAD the facts were read at, which a report does not move because it writes only under .dabbler/. Then the report opens, with the same Copy and open offer as now. Where no stop stands, the dialog is as it is today.

Step 2 -- a report that could not be written does not hold the rollback up, and is not hidden. If defect-report refuses or fails, the person is told so in its own words and asked once whether to roll back anyway: the default keeps the session, because rolling back is what makes the report impossible.

Step 3 -- the report says a rollback followed. defect-report takes a switch, --rolling-back, and the report's Where section gains one line: the person chose to roll the session back rather than go on. Nothing else of the rollback is in the report: no count of commits, no author, no path, no reason.

Step 4 -- a person at a terminal is told. dabbler session rollback --help and docs/driving-a-session.md say that a stop is reported before it is rolled back, and name the command.

Step 5 -- the number. version.json goes to 3.35.0 (a minor: a person has a choice they did not have), stamped with npm run stamp:version, and the changelog's 3.35.0 section says what sessions 334 to 336 changed for a person.

Non-goals. Sending anything: the person reads the report and sends it themselves, as now, and no code posts an issue. A report after the rollback, read from a superseded run record. A report of a rollback from no stop, or of a completed session rolled back with nothing standing: a session that ran to its end and was not wanted is feedback of another kind, and gets a session of its own if it is asked for. Asking the person for a reason at the rollback. Any change to what a rollback does to the tree, the ledger or the run records. Any change to what is scrubbed or to the Primary Reviewer's check.

Why. The operator asked, several sessions ago, that starting with Dabbler begin at the Configuration. Session 303 delivered that only once a folder is open: its plan said "with no folder open at all, both welcomes stay as they are", and listed the no-folder case as a non-goal. So a person who opens VS Code, or a new window, and chooses Dabbler sees an Open Folder button and a sentence about what a folder would show. The operator's words, 2026-11-14: "I don't understand why a user can't see and set the machine default configurations IMMEDIATELY prior to a folder opened or project being started."

Nothing stands in the way. The Solution Explorer's provider returns early without a workspace root, and so does each Configuration command, but the reading is already taken with no folder (activation reads it from the home directory to warn about a missing engine CLI), the write that touches the machine's default alone already exists (mine), and the catalog refresh needs no folder. A machine whose defaults are set first then hands them to every solution it sets up, which is the "Copilot needs a model" stop of 2026-11-10 removed rather than explained.

The buttons say too little as well. "Set Up New Project" is the only button for a person whose repository is ten years old, where nothing is new, and the person who has a folder or a repository already is offered "Open Folder" with no word about what follows.

"Set Up New Project" keeps its name. The operator proposed "Set Up New Solution", to match the Solution Explorer. Four advisors in two rounds (docs/design/consults/round25-* and round26-*) were asked, and none would use "Solution": it is a .NET word, and the same operator wants a person writing a policy or a story to be able to start here. "Project" fits a program, a policy and a book alike, and it is the word already in every document. This session ships alone, as 3.34.0: it answers a failure already seen in the field and depends on nothing else planned.

Step 1 -- the machine's reading, with no folder. The configuration reading takes no repository: the flag and checkout layers are absent, and what it reports is the machine's preferences.json over the distribution's defaults, with the catalog as it stands. It is a reading of its own and not the home directory read as a repository, so a .vscode/settings.json that happens to sit in a person's home folder decides nothing. With no workspace root the Solution Explorer renders the Configuration root alone, labelled as this machine's defaults, and the unread-catalog reading of session 303 runs there as it does with a folder.

Step 2 -- every row writes the machine's default. With no folder, each Configuration command writes with mine and names no repository; configure accepts that pair. A row that has no machine default to write is left out rather than shown and refused. The section's label and the toast both say what a machine default is, in one sentence: it applies where a repository has no choice of its own, and it does not replace a choice already saved in one.

Step 3 -- the buttons, in the Work Explorer. Once the Configuration always shows, the Solution Explorer is never empty and VS Code never shows its welcome, so that entry is deleted and the Work Explorer's welcome carries the buttons:

  • No folder open: Set Up New Project first, then Open Existing Folder or Repository.

Open Existing Folder or Repository asks one thing -- a folder on this machine, or a repository to clone -- and hands each to VS Code's own command (vscode.openFolder, git.clone). The window that opens makes the offer it already makes for a folder that is not set up, and that toast's button takes the same label as the welcome's.

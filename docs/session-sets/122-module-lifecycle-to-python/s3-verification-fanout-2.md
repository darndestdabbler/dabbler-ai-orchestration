**ISSUES FOUND**

**Issue 1:** The capability probe can validate `.venv` while module launchers still run a different explicit interpreter.
- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/src/utils/aiRouterInstall.ts:335-344,367-429`, `tools/dabbler-ai-orchestration/src/utils/pythonInterpreter.ts:115-126`, `tools/dabbler-ai-orchestration/src/utils/routerCli.ts:218-229`, `tools/dabbler-ai-orchestration/src/utils/moduleLifecycleCli.ts:94-112`, `tools/dabbler-ai-orchestration/src/commands/gitScaffold.ts:596-605`, `tools/dabbler-ai-orchestration/package.json:483-487`
- **Failure scenario:** A developer sets `dabblerSessionSets.pythonPath` to a valid non-venv Python executable, which the setting explicitly permits. Setup creates and probes `<workspace>/.venv`, reports install success, then default-module creation and later module commands resolve the explicit system Python instead of `.venv`, so `python -m ai_router.modules` fails for a project that supposedly passed the router guarantee. This is probable for users who set an absolute Python path because Python is not on PATH or they need a specific Python version.
- **Acceptance criterion:** `JUDGMENT - In a fresh workspace with dabblerSessionSets.pythonPath set to a valid non-venv Python executable, setup must either probe and use the same effective module-launcher interpreter for default-module creation and later module commands, or fail before default-module creation; it must not probe .venv while launchers resolve a different interpreter.`
- **Details:** **Violation:** the spec requires “probe the same venv interpreter the launcher will use” and ends with “a project that finishes setup can run every module command.” **Impact:** the main release-gate promise can be false for a supported configuration, so a reasonable reviewer should not merge. **Evidence:** install probes `venvPython(outcome.venvPath)`, but `runRouterCli` independently calls `resolvePythonInterpreter`, whose precedence returns the explicit setting before workspace `.venv`. **Correct answer:** make launcher resolution and probe target the same verified interpreter, or fail setup when the launcher interpreter is not capable.

**Issue 2:** The dogfood lane does not prove the promised default module is created from a fresh setup.
- **Category:** Completeness
- **Severity:** Major
- **Evidence paths:** `docs/session-sets/122-module-lifecycle-to-python/spec.md:289-312`, `tools/dabbler-ai-orchestration/src/test/dogfood/routerFloorProvisioning.test.ts:193-239,301-348`, `tools/dabbler-ai-orchestration/src/test/suite/gitScaffoldDefaultModule.test.ts:374-397`
- **Failure scenario:** `npm run test:dogfood` can pass even if the real setup path cannot create the default module with the newly provisioned venv, because the dogfood only calls `installAiRouter`, manually ensures `docs/modules.yaml`, and asserts `decideDefaultModuleScaffold(...) === "scaffold"`. This is probable because the dogfood’s current code never invokes the Python-backed module creation in the real install scenario; Issue 1 is exactly the kind of integration failure it misses.
- **Acceptance criterion:** `JUDGMENT - The dogfood lane must drive the real setup/default-module creation from a fresh empty folder, including the failed-install retry path, and assert the default module manifest entry plus its plan/decomposition session-set files exist, not merely that decideDefaultModuleScaffold returns "scaffold".`
- **Details:** **Violation:** the spec requires a clean project to finish setup with “the default module present” and says the ends-with state is “each proven from a fresh empty folder.” **Impact:** the release gate lacks the proof it claims, so merge confidence is materially overstated. **Evidence:** the dogfood asserts install/probe/version and gate decisions only; the real writer is exercised elsewhere with seams/fake install, not with the real venv/pip dogfood. **Correct answer:** the dogfood must execute the end-to-end setup path through actual default-module creation.

ISSUES FOUND

### Issue 1: Enabling the physical pointer selects the backend already measured to black-frame VS Code

- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js`, `tools/dabbler-ai-orchestration/scripts/obs-capture.js`, `docs/session-sets/113-narrated-video-walkthroughs/s7-cursor-capture-backends.json`, `docs/session-sets/113-narrated-video-walkthroughs/s7-pointer-outcome.md`
- **Failure scenario:** Every VS Code run with `physicalPointer` sets `needCursorVisible: true`; `ObsCaptureSession.configure()` deterministically maps that to BitBlt. The committed measurement reports BitBlt's `windowCorrelation` as `0` and `windowPresent: false`, matching the known black-frame behavior of hardware-accelerated Electron. Thus a typical pointer-enabled recording loses the product UI entirely.
- **Acceptance criterion:** `JUDGMENT - A real Windows run with the physical-pointer option must record both the VS Code workbench and cursor, pass the artifact visibility check, and use a capture backend that has passed the applicable capture-pilot criteria.`
- **Details:** **Violation:** The session must “show the pointer” on the VS Code path, while the decision record claims “no backend was swapped.” **Impact:** The option intended to fix cursorless recordings instead produces a black recording, so the main feature is unusable and should block merge. **Evidence:** `record-vscode-walkthrough.js` passes `needCursorVisible` for both pointer and control runs; `obs-capture.js` selects `CAPTURE_METHOD_BITBLT` whenever that flag is true; the measurement says that backend does not contain the workbench. The correct fix is not to route production pointer captures through the known-black backend; use a backend proven to capture both UI and pointer, or keep the feature unavailable until one exists.

### Issue 2: The speed-ramp treats every unmarked gap as waiting, so ordinary human work is compressed

- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `ai_router/speed_ramp.py`, `ai_router/tests/test_speed_ramp.py`, `docs/tutorials/single-module-walkthrough.md`
- **Failure scenario:** In the required human-driven tutorial, the operator reads, types, edits files, and responds to AI between sparse lifecycle timestamps. `build_segments()` protects only a three-second pad around each instantaneous mark and compresses every sufficiently long gap, often at up to 40×. Human activity between those marks is therefore likely to become an unreadable fast-forward even though it was not waiting.
- **Acceptance criterion:** `JUDGMENT - Given a representative human session containing both an active-work interval and a bounded known-wait interval, the generated plan must leave the complete active interval at 1× and compress only the known wait.`
- **Details:** **Violation:** The requirement says waiting must be “derived from the framework's own record” and “never compress an interval where something happened.” **Impact:** The resulting tutorial can accelerate the very authoring and decomposition work it is supposed to demonstrate, materially defeating the tutorial objective. **Evidence:** The implementation does not interpret event types, pair start/end records, or identify wait states; `_quiet_segments()` is called for every gap between padded timestamps. Its tests establish only that no timestamp itself falls inside a compressed segment, not that active intervals remain uncompressed. The walkthrough even admits that reading and typing can look identical to waiting. The correct implementation must derive bounded wait intervals from event semantics or collect additional active-work evidence, rather than equating absence of timestamps with waiting.

### Issue 3: The pixel checker can pass without proving that a cursor is visible

- **Category:** Correctness
- **Severity:** Major
- **Evidence paths:** `tools/dabbler-ai-orchestration/scripts/check-pointer-visible.js`, `tools/dabbler-ai-orchestration/scripts/record-vscode-walkthrough.js`, `tools/dabbler-ai-orchestration/scripts/measure-pointer-visibility.js`, `docs/session-sets/113-narrated-video-walkthroughs/s7-pointer-visibility-vscode.json`
- **Failure scenario:** Moving the real pointer onto a normal button or tree row changes that target's local hover styling even when the capture backend omits the cursor. The checker sees target-local change, sees no change in its unrelated top-left control crop, and reports a pass. Repeated or nearby targets also commonly become `indecisive`; the checker still returns `PASSED` if only one probe passes and all remaining probes are indecisive.
- **Acceptance criterion:** `JUDGMENT - A recording with no cursor pixels but a target-local hover change must fail, every required click must be conclusively measured before the run can pass, and frame timestamps must be synchronized from an actual recording-start/end anchor rather than an unrelated last event.`
- **Details:** **Violation:** The required proof is that “a pointer is visible in the recorded frames near the target's bounding box at the moment of the click.” **Impact:** The instrument can certify a cursorless artifact, making both its positive result and falsifier misleading. This directly undermines the load-bearing artifact proof. **Evidence:** The pass condition says only that “something appeared at the target”; it does not identify cursor pixels or distinguish local hover effects. Its final verdict ignores `indecisive` probes when there are no explicit failures. The committed VS Code run already contains two indecisive probes out of six, showing this is not hypothetical. Additionally, `recordingStartOffsetMillis()` assumes the final event coincides with the file's end without checking the event type or capture-stop boundary. The checker needs cursor-specific discrimination, conclusive coverage of every required action, and reliable clock alignment.

## NITS

- **Nit:** `record-vscode-walkthrough.js` catches every physical-pointer initialization or calibration error and continues recording without a pointer. An explicitly requested pointer capture should fail closed; otherwise a mixed-DPI, foreground-window, or PowerShell failure can produce the expensive pointerless artifact the ordering rule was intended to prevent.
- **Nit:** Physical-pointer cleanup resets the topmost window state before calling `physical.close()`, despite the comment promising pointer restoration “FIRST.” It also ignores the restore PowerShell process's exit status and logs that the pointer was released even if restoration failed.
- **Nit:** `calibratePhysicalPointer()` chooses its calibration probes using the same `(screenX + client) * devicePixelRatio` estimate the comments identify as invalid on mixed-scale secondary monitors. It has no stated retry despite claiming a wrong estimate “costs a retry.”
- **Nit:** VS Code probe coordinates use `result.window.scaleFactor` rather than the measured calibration scale. Workbench zoom or mixed-DPI mappings can therefore move the physical pointer correctly but make the artifact checker crop the wrong pixels.
- **Nit:** `collect_marks()` silently skips malformed JSON on every JSONL line, not only a half-written final line. A corrupt middle event can therefore disappear and cause its surrounding interval to be compressed.
- **Nit:** The speed-ramp accepts either event source being absent despite claiming derivation from both records. A partially written or missing ledger silently weakens the plan rather than being reported as incomplete evidence.
- **Nit:** CLI numeric settings are not validated for finiteness or sensible ranges. Negative padding, negative thresholds, zero rates, or `NaN` can generate malformed or unprotected segments instead of a `SpeedRampError`.
- **Nit:** `build_segments()` removes every segment of 50 ms or less. Such an interval then vanishes from the output rather than tiling the whole recording, contrary to the plan-shape invariant.
- **Nit:** `apply_plan()` validates neither segment ordering/coverage/rates nor that the input duration and identity match the recording used to build the plan. A stale or manually damaged plan can be applied to the wrong similarly named session video.
- **Nit:** Failed or interrupted ffmpeg application can leave a partial target after `-y` has replaced an earlier file; no temporary output and atomic rename are used.
- **Nit:** Timestamp, `ffprobe`, malformed-plan, and filesystem errors other than `SpeedRampError` escape the CLI as raw tracebacks rather than actionable refusals.
- **Nit:** The synthetic pointer is a normal body child. Top-layer dialogs/popovers render above all document stacking contexts, so the maximum `z-index` does not guarantee pointer visibility over common modal controls.
- **Nit:** Assigning the SVG through `innerHTML` can fail on pages enforcing Trusted Types. Because the synthetic pointer is now the web recorder's default, such a page can turn pointer injection into a recorder failure.
- **Nit:** The publication checklist does not explicitly require checking the finished video for notification toasts, even though toasts are an enumerated mandatory item; it only gives pre-recording prevention advice. Its suggestion to “scrub” long videos can also miss transient one-frame disclosures.
- **Nit:** The committed BitBlt evidence reports `cursorChangedFraction: 0` and `cursorPresent: false`, while comments and prose assert that BitBlt displayed an arrow. That cursor-specific claim is not supported by the cited measurement.
- **Nit:** The changelog's claims about a real Session 6 plan and a 22.52-second end-to-end encode have no corresponding committed ramp plan, application report, or probe artifact in the presented work.
- **Nit:** The extension test claiming to ensure walkthrough documents are not treated as session sets checks for `publication-safety-checklist` while scanning only `docs/session-sets`; the checklist lives under `docs/walkthroughs`, making that assertion effectively vacuous.

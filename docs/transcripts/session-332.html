Session 332 of 337: The Work Explorer stops freezing the window

Scope: tools/dabbler-ai-orchestration/src/utils/projection.ts (projectionCacheKey, taskRecordInputs), tools/dabbler-ai-orchestration/src/utils/fileSystem.ts (discoverRoots, listGitWorktrees, scanRepositories), tools/dabbler-ai-orchestration/src/providers/WorkExplorerTreeProvider.ts (refresh), tools/dabbler-ai-orchestration/src/extension.ts (the watchers and the poll), projection.test.ts, fileSystem.test.ts, workExplorerTreeProvider.test.ts (new), version.json and the manifests npm run stamp:version writes, tools/dabbler-ai-orchestration/CHANGELOG.md

An emergency fix, before the walks. The operator, 2026-11-16: Dabbler "seems to be running really slowly", and a Start in chromatic-notation-configurator did nothing the first time and took a couple of minutes the second. Every session in every repository pays for this, and sessions 334 and 335 would walk a framework that freezes the window they are walked in. So it comes first, and ships alone as 3.34.1.

Why. Measured on this machine, 2026-11-16, from VS Code's own logs:

  • Since 2026-11-14, about fifty UNRESPONSIVE extension host reports name darndestdabbler.dabbler-ai-orchestration, each with a CPU profile saved under %TEMP%. Across 53 profiles, 73% of the time attributed to the extension is in one chain: getChildren > scan > scanRepositories > ProjectionCache.get > projectionCacheKey.
  • The freezes come every 30 seconds or so, in every open window at once, and last 1 to 8 seconds each. The chromatic window registered session 73 at 07:08:26, and its run started at 07:11:11. In between, the window froze for about 40 seconds, in pieces of up to 8.6.
  • The key decides only whether to ask the router again, yet working it out stats five files for every session the repository has ever run: 1,305 stats here (580 of them for files that do not exist) and 360 in chromatic, all synchronous on the extension host's one thread. A closed session's records never move, and they are stat'ed on every scan for good, so the cost grows with every session closed. The same sweep takes 17 ms in a plain node, and 230 to 490 ms in the profiles. Why the host is that much slower is not known, and nothing here depends on knowing.
  • Every scan, and every 30-second poll before it (bindWatchers), also runs git worktree list through execFileSync. That is two blocking git processes per poll per window.
  • Every write to a watched file starts a full scan of its own, with nothing to merge a burst. Starting a session writes in bursts.

Step 1 -- the key reads what can move. The key is the four sessions-root files, the runs directory's own mtime (a run directory added or removed moves it), and the five records of one run: the run the cached projection named current, or the highest-numbered run when there is none. The number of files it reads no longer depends on how many sessions the repository has run. This rests on one constraint, and the session confirms it from the writers before relying on it: a closed session's run records move only with sessions.json or activity-log.json, which are in the key. A writer that breaks that keeps its file in the key, and the session records which one it was.

Step 2 -- git does not block the window. listGitWorktrees runs git asynchronously. Roots are discovered once per poll tick, workspace-folder change or explicit refresh, and not once per scan: the poll's watcher binding and the scan take the same list.

Step 3 -- a burst is one scan. refresh() merges the calls that arrive within a quarter of a second into one repaint. The explicit refresh command, refresh(true), still repaints at once.

Step 4 -- the number. version.json goes to 3.34.1 (a patch: nothing a person does changes, and the window stops freezing), stamped with npm run stamp:version, and the changelog's 3.34.1 section says so in a sentence.

Non-goals. The router's in-process projection (buildProjection, about 6% of the time sampled) and the scan's other readers (currentActivity, uncollectedWords, about 10%). They were measured and are left alone; if the logs still show the host unresponsive after this release, they get a session of their own. Moving the scan to a worker thread. Any change to dabbler.refreshSeconds or its default. Explaining the Start that did nothing: no trace of it was found (no run directory and no write), and if it happens again after this release it becomes a session of its own.

Tests.
